# Expressive menus that scroll within each group and open at the top

This pass reworks the F2E design-system layer on the five points the previous review raised. `ExpressiveMenu` no longer scrolls the popup column: each group scrolls inside its own container, and a private `MenuGroupsMeasurePolicy` stacks the groups `MenuDefaults.GroupSpacing` apart, at their natural heights when they fit and otherwise at shares of the window proportional to those heights. The scroll states are remembered inside the popup content, so every opening starts at the top. `MediumButton` provides the medium label style to its content, the plan's section 4 calls the layer partly done and states its rule, and the new `ExpressiveMenuTest` covers dismiss-then-act, two groups in a short window, and reopening. Checked against the alpha18 and foundation 1.11.3 sources, all five fixes hold, and the Study menus and medium buttons lay out as before.

Watch for: the policy takes each group's natural height from `maxIntrinsicHeight`, which alpha18's menu items overstate for any item with a leading icon: their measure policy defines no intrinsics, so the label is measured at zero width. A grouped menu with icons would be split on inflated heights and could scroll a group while the window still has room (confirmed by code). The flag menu, the only menu with icons, is a single group, so nothing on screen changes and this does not block.

**Verdict**: APPROVED

## High-level view

The scroll states now live in the `DropdownMenuPopup` content, which is composed only while the menu is open or animating (Menu.kt:247), so the flag, more-card-actions and always-composed long-press menus all reopen at the top. Each group's `verticalScroll` lands on the Column inside the group's Surface (Menu.kt:331). The clip therefore sits inside the shape, the 3 dp shadow comes from the Surface's own `graphicsLayer(clip = false)`, and neither the new `Layout` nor the popup column clips, which is the geometry the single-group menus already had at HEAD. That rests on alpha18 applying `DropdownMenuGroup`'s `modifier` to the inner Column rather than to the Surface, an undocumented detail to recheck at the B-path upgrade (confirmed dependency).

For a single group the proportional share is the whole room, so the flag and long-press menus still measure `min(natural, window)` as at HEAD. The more-card-actions menu's two plain groups need about 270 dp at 2× font in English, so they keep their natural heights even in a 411 dp landscape window. The policy's weak point is its input: intrinsic heights are exact for plain items but inflated for items with a leading icon, which would misplace the split in a future grouped menu with icons (confirmed by code, non-blocking).

`MediumButton`'s content overload merges `textStyleFor(MediumContainerHeight)`, which is titleMedium, over the Button's labelLarge. `AnswerButton`'s texts set explicit styles, so they are untouched, and the label overload's text inherits the style it used to pass itself; only the centered Show answer label moves, by a sub-pixel. Section 4 of the plan now names the single-call APIs that stay direct. The F2E entry's "one place" claim matches the code: `DropdownMenuPopup`, `DropdownMenuGroup`, `MenuDefaults`, `shapesFor`, `contentPaddingFor`, `textStyleFor` and `MediumContainerHeight` appear only in `designsystem`.

### Leading icons inflate the heights `MenuGroupsMeasurePolicy` shares

(confirmed by code; no current menu shows it) The policy chooses between natural and proportional heights from the groups' intrinsics:

```kotlin
val heights = measurables.map { it.maxIntrinsicHeight(constraints.maxWidth) }
val total = heights.sum()
val room = (constraints.maxHeight - gaps).coerceAtLeast(0)
// per group:
val height = if (total <= room) heights[index] else (heights[index].toLong() * room / total).toInt()
```

The query passes through the group's Surface, its scroll (ScrollNode forwards the width for vertical intrinsic heights) and its Column down to each item's `Layout`. That layout's `DropdownMenuItemMeasurePolicy` (Menu.kt:1677) defines only `measure`. The default `MeasurePolicy.maxIntrinsicHeight` runs that measure with `Constraints(maxWidth = width)` over `DefaultIntrinsicMeasurable` stand-ins, and a stand-in measured for a height reports the full constraint width as its own. For an item with a leading icon, `NoTrailingIconMeasureResult` subtracts the ghost icon's reported width, which is the whole row, and measures the label with `Constraints.fixedWidth(0)`. `Text`'s intrinsic height at width 0 comes from its paragraph laid out at zero width, which wraps after every character. "Turquoise" thus counts as nine lines of labelLarge, roughly 200 dp with the item's 12 dp vertical padding, against the 48 dp the item takes. Items without icons go through `JustTextMeasureResult`, which passes the real width, so their numbers are exact.

```
group intrinsic = Σ item intrinsics
  plain item → label measured at the row's width   → exact
  icon item  → label measured at zero width        → several times the real height
```

Overstated heights do no harm in the fitting branch, because each group gets a cap above its natural height and `verticalScroll` wraps its content. The harm is in the branch decision and in the shares. Take one group of icon items and one of plain items in a window where their real total fits. The inflated total can exceed the room, so the policy switches to proportional shares: the icon group gets more than it uses, and the plain group is capped below its natural height and scrolls while part of the window stays empty. Two icon groups mislead it the same way when their labels differ in length, since the inflation grows with the characters per label. Either way, the KDoc's "while the window has room, each is as tall as its items" no longer holds. No current menu has that shape: the flag menu is the only one with icons and is a single group, and the other two have none.

### Test coverage

Each new `ExpressiveMenuTest` case pins one fix. The reopen case (ten items at 914×411 dp, 2× font) fails if the offset outlives the popup. The two-group case (six items each, same window) fails under the previous pass's whole-column scroll, where B1 would start out of view. The dismiss case pins the `onDismissRequest`-before-action order that StudyScreen's long-press menu relies on, and checks that the popup goes away. The full run was reported as 241 tests in 29 classes, all green. I did not re-check that count, because the screenshot compare has since overwritten the result XMLs on disk. In the failed targeted run (`f2e-tests2.log`), all eight StudyPanesTest failures are `UnsatisfiedLinkError` in `NativeMethods.openBackend` and ExpressiveMenuTest passes. That fits the sandbox-ordering explanation, and the NATIVE-graphics StudyComponentsTest is unchanged by this diff. The compare differs only in the study_error variants (the expected F2D title) and the study_question variants (the edges of the Show answer glyphs).

Not tested: leading-icon items in a multi-group menu (the case above), since `ExpressiveMenuTest` builds only plain items. The groups' shadows are also untested: Robolectric does not render them, so the restored shadows are checked by structure only and belong on the G1 device list.
