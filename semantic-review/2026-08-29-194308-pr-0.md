# Attempt-scoped startup sync gate for the Expressive handoff

The follow-up replaces the activity-wide completion signal with generation-scoped startup sync state and persists enough phase information to separate retryable in-flight recreation from terminally blocked outcomes. Normal retries get new generations, conflict resolution reuses only the recorded conflict generation, and completion is accepted only for the active generation. Sync success now follows cache clearing, subscriber notification, and refresh, while missing auth, metered cancellation, exceptions, and cancellation block the gate. **Watch for:** **low, confirmed** the tests still bypass production sync outcomes and do not directly lock down recreation, terminal failure categories, conflict continuation, or post-finalization cancellation.

**Verdict**: APPROVED

## High-level view

Each Expressive login startup owns a monotonically increasing sync generation. New login intents invalidate the previous active generation, same-gate retries allocate another generation, and nonmatching callbacks are ignored.

Saved state persists pending/blocked phase, the generation counter, and an awaiting-conflict token, but not an active generation. Terminal outcomes remain inert after recreation; interrupted active work retries under a new generation that the destroyed attempt cannot release.

`FULL_SYNC` records the current token without completing the gate. Selected full upload/download reactivates that token, and only successful post-sync finalization completes it.

Classic startup retains automatic sync, scheduler v1 blocks Expressive until upgrade, and the handled bit is set before destination launch. Focused tests cover stale `onNewIntent` completion, same-gate failure/retry, classic routing, scheduler blocking, and exactly-once handoff.

## Attempt generations reject stale completion

The gate has separate counter, active-attempt, and conflict-attempt identities (`DeckPicker.kt:1853-1867`). `onNewIntent` clears previous active/conflict identities before requesting a new login sync (`DeckPicker.kt:2599-2617`), and completion/failure require the supplied token to equal the active token (`DeckPicker.kt:1883-1907`). The same-gate retry path increments the generation, so stale completion from an older sync, login intent, or failed attempt cannot release the current gate. Tests cover the new-intent and failure/retry races (`DeckPickerTest.kt:994-1059`).

## Blocked terminal state and recreation

Missing credentials fail the allocated attempt before the login error; declining or dismissing the metered warning invokes the same transition (`DeckPicker.kt:2127-2146`). Missing auth during `SyncAuth` construction, backend/finalization exceptions, and coroutine cancellation also block the attempt (`Sync.kt:104-154`).

Pending, blocked, the counter, and any conflict token are saved (`DeckPicker.kt:1532-1548`), and recreation schedules Expressive login auto-sync only when pending and not blocked (`DeckPicker.kt:505-515`, `DeckPicker.kt:538-543`). A user-triggered normal sync clears blocked state and starts a new generation (`DeckPicker.kt:1857-1861`). Because active generation is not restored, interrupted work retries with the persisted counter plus one; the destroyed activity's prior token cannot match the replacement activity's active generation.

## Conflict continuation and post-sync finalization

Normal sync maps `FULL_SYNC` to `AWAITING_CONFLICT_RESOLUTION` (`Sync.kt:170-237`). The handler records that generation and clears active state (`Sync.kt:136-138`, `DeckPicker.kt:1870-1881`); choosing full upload/download reactivates only the stored token (`DeckPicker.kt:1862-1867`).

Cache clearing, subscriber notification, and refresh precede completion (`Sync.kt:139-144`). Exceptions or observed cancellation in sync/finalization reach failure instead (`Sync.kt:145-147`), so they do not invoke successful completion.

## Classic, scheduler-v1, and exactly-once behavior

Classic startup continues into `automaticSync()` (`DeckPicker.kt:1821-1831`), while Expressive remains gated on scheduler v2 (`DeckPicker.kt:1834-1850`). The handled flag is checked and set before `startActivity`, preserving exactly-once behavior under repeated reevaluation/completion (`DeckPicker.kt:1910-1926`). Tests cover classic login, scheduler-v1 blocking, and repeated completion after handoff (`DeckPickerTest.kt:966-992`, `DeckPickerTest.kt:1061-1100`).
