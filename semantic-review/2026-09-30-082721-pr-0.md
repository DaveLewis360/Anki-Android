# Anki night-mode classes for Study cards, with card motion gated on page commit

This pass verifies the fixes for the previous NEEDS_CHANGES review. `CardMotion` now records that a leave hid the pane, and a pure `cardPaneStep(side, visible, hidden, animationsOff)` decides each step. An answer rendered while the pane is hidden therefore keeps fading out, resuming an interrupted fade, until it commits or the 1.5 s fallback fires. At animator scale 0 every step settles, so the WebView swaps documents in place. The nits are fixed, with the KDoc checked against `CardAppearance`, card_template.html and card.js, and `visibleRenderKey` is cleared along with the WebView. The 179 `com.ichi2.anki.ui.expressive.*` tests (18 classes) pass with 0 failures in a run that started after the last edit, and `git diff --check` is clean.

**Watch for:** no new behavioral issues. **Confirmed:** there is still no device run. The removed KDoc blamed the glitches on container-level motion racing the WebView's loading. The commit gate targets that race, but only a device run can show whether the glitches are gone. **Confirmed (nit):** the new `CardMotion` KDoc describes the leave backwards, and the class KDoc of `CardPaneStepTest` promises more than the step function does.

**Verdict**: APPROVED

## High-level view

`hidden` is true from a leave until the next settle starts. That is exactly the window in which the WebView may still draw the previous card, and it is the only time the answer side now waits for its own commit. These orderings were traced: a reveal during the leave, a reveal in the same frame as the question's commit, the Question-then-Answered refresh pair (including when Compose sees only the second), and a non-card interlude. None of them draws another card at full alpha, except through the 1.5 s fallback. The answer path now shares that fallback, and it still fails open.

The animations-off check reads the `MotionDurationScale` that the window recomposer puts into every effect's context. It therefore follows the system animator scale, and the pane never goes blank. The cost is the same as in Classic: the previous card stays on screen until the next document commits. A reveal that comes before the question commits shows the previous answer until the new answer commits.

The `visibleRenderKey` reset covers the only way a render key can repeat after the WebView has dropped its document. That happens when the same question renders again after a non-card state, and without the reset it would enter over `about:blank`. Renderer recovery changes the key's generation, so it can't repeat a key.

`CardPaneStepTest` covers 15 of the 16 inputs. The missing one is a question that becomes drawable while the pane isn't hidden, which is what a commit after the fallback looks like. Not tested: `CardMotion`'s `hidden` bookkeeping, the fallback timer and the scale read. This pass checked those by trace only.

### Reveal before the question commits

```
Question(N)  → HIDE_UNTIL_VISIBLE: leave sets hidden, alpha → 0      WebView draws A(N-1)
reveal       → question effect cancelled mid-fade, hidden stays set
Answered(N)  → cardPaneStep(ANSWER, visible=false, hidden=true) → HIDE_UNTIL_VISIBLE
             → leave resumes from the current alpha; render(A(N)) aborts Q(N)
A(N) commits → cardPaneStep(ANSWER, visible=true, …) → SETTLE: hidden cleared, alpha → 1
```

**Confirmed:** if the fallback already fired on Q(N) before the reveal, `hidden` is clear. The answer then settles over A(N-1), which stays at full alpha until A(N) commits. The fallback's fail-open behavior now reaches the answer side too.
