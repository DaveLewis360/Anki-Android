# Safe-origin Expressive reviewer re-review

The corrected reviewer moves collection media and Android assets onto the restricted appassets origin, classifies WebView touch targets before card gestures, and keys page completion and media readiness to the current render. Renderer generation now participates in render identity, while lifecycle, renderer-gone recovery, replay/autoplay gating, generated video URLs, TTS, and missing-user-action UX run through the production path. Four prior findings are closed, but internal navigation still receives the render that is ready when the callback is delivered rather than an identity carried by the emitting document. **Watch for:** **medium, likely** a delayed internal navigation from the replaced document can be relabeled as the newly ready render and control its media/UI.

**Verdict**: NEEDS_CHANGES

## High-level view

The safe origin keeps assets in a dedicated namespace and media at the origin root, preserving relative card resources and generated video URLs without restoring file access. Normalized traversal and unknown same-origin requests become 404 responses, while unrelated HTTPS hosts retain network fallback.

Each load has a query-tokenized document URL, and only matching page-start/page-finish callbacks promote it. This matches WebView's HTTP(S) `loadDataWithBaseURL` contract and preserves sibling/root-relative resource resolution; renderer recreation also changes the render key through renderer generation.

Touch classification combines synchronous WebView hit testing with DOM lookup, and media playback requires current-render plus page-ready equality. The remaining gap is that internal navigation is labeled from global `readyRenderKey`, which proves readiness but not which document emitted the request.

## Ready-time labeling does not identify the document that emitted a media command

**Medium, likely:** both `shouldOverrideUrlLoading` overloads forward only the requested URI to `handleNavigation()` (`ExpressiveCardWebView.kt:284-298`). Once the current page has finished, `handleNavigation()` reads global `readyRenderKey` and attaches that key to every internal URI (`ExpressiveCardWebView.kt:338-355`). The controller can validate only that supplied key, so `playsound`, `videoended`, `videopause`, `tts-voices`, and `missing-user-action` accept a stale command if the client labels it with the current key (`ExpressiveReviewerMediaController.kt:95-124`).

Reproduction: finish render A; retain an A-originated `playsound:q:0` or `videoended:q:0` callback; begin and finish render B; then deliver the retained callback through `shouldOverrideUrlLoading`. The client supplies B's key, so the controller passes its current/page-ready checks and resolves B's `q:0` or advances B's active video. The focused test sends stale navigation only while B is not ready, then sends an indistinguishable navigation after B is ready (`ExpressiveCardWebViewTest.kt:216-249`); it verifies readiness gating but not source-render binding.

The document token must travel with every command. Injecting it into generated internal URLs or using a token-bound JavaScript bridge would allow the client/controller to reject delayed A commands after B becomes ready; video completion and dialog commands need the same binding as `playsound`.
