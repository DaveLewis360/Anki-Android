# Race-safe durable ownership for Expressive sync

The Task 11 P1 follow-up changes sync enqueueing from replacement to durable adoption, separates pending candidates from accepted attempts, and repairs process-death windows from WorkManager state. Terminal acknowledgement now commits to the durable attempt store before saved state records completion, account form credentials remain memory-only, and full-sync cancellation aborts the backend before collection reopen. The prior P2 about `ExpressiveSyncViewModelTest.kt` is excluded because the file predates Task 11 and was an allowed existing test target. Watch for: no remaining blocking concern in the reviewed P1 scope.

**Verdict**: APPROVED

## High-level view

`SyncWorker.start()` serializes in-process starts, uses `ExistingWorkPolicy.KEEP`, and returns the IDs of the actual accepted logical attempt. A candidate remains pending until its collection request exists in WorkManager; rejection preserves the previous accepted record and adopts the current unique-work owner.

Gateway startup reconciles pending and accepted metadata against exact WorkManager IDs. Recovery tags contain only orchestration identifiers, and missing accepted work is repaired from the unfinished tagged owner or cleared rather than projected as queued indefinitely.

Terminal acknowledgement is an exact, idempotent store commit, and the ViewModel writes its saved-state marker only after that commit succeeds. `ExpressiveAccountViewModel` no longer receives a `SavedStateHandle`; unfinished credentials are memory-only, while authenticated identity is reloaded through the credential-backed gateway.

Full upload/download registers cancellation abort while the backend operation owns the closed collection. `cancelSync()` is guarded by a per-worker atomic flag, and reopen remains guaranteed after the abort request.

## Accepted-attempt ownership across enqueue and process death

The enqueue path writes a non-secret pending record, enqueues the unique collection→media chain with `KEEP`, waits for WorkManager completion, and promotes only after the candidate collection ID can be read back. If KEEP rejects the candidate, pending metadata is discarded and reconciliation returns the existing owner’s attempt, collection, and media IDs.

Startup reconciliation discards a pending record with no WorkInfo and promotes one whose request reached WorkManager. An accepted record whose exact work disappeared is repaired from the tagged unfinished unique owner or cleared, closing both enqueue crash windows without converting missing work into an indefinite queued state.

Existing tests cover same-process adoption, unaccepted-pending cleanup, accepted-before-promotion recovery, exact idempotent acknowledgement, and acknowledgement retry after recreation.

## Abort-before-reopen for one-way sync cancellation

Full sync installs a cancellation callback immediately after closing the collection and invokes the same guarded abort from the direct cancellation catch. The callback requests backend cancellation before the `finally` block reopens the collection; the atomic guard prevents the worker-level cancellation catch from issuing a second abort.
