# Classic migration fail-closed finalization boundaries

The latest migration changes make completion recovery durable, normalize public recovery failures, and close activated collections through a strict queue-held API before filesystem recovery. Cancellation after staging may have activated now crosses the same cleanup boundary as ordinary finalization failures. All four prior issues are closed, and no new P0/P1/P2 behavioral regression was found in the requested three-file scope. Watch for: no remaining blocking concern; focused commit-failure, close-failure, and activation-return-cancellation tests are absent, so these paths were verified by direct code trace and compilation.

**Verdict**: APPROVED

## High-level view

A `COMPLETE` journal now commits `expressive.classic_migration.completed` before any recovery artifact is deleted. Public recovery rethrows cancellation and maps other operational exceptions to `Blocked`.

Post-activation cleanup uses a strict close under the collection queue. The reference is cleared only after a successful close, preserving the guard when close fails.

Activation is inside the finalization `try`, with `stagingActivated` recorded immediately after the stage-to-target rename. Activation-return cancellation therefore triggers a `NonCancellable` strict close before rethrow.

## `COMPLETE` recovery ordering — prior issue 1 CLOSED

**CLOSED, confirmed:** `ExistingProfileMigrationService.activate()` (`ExistingProfileMigrationService.kt:150-201`) executes `writeJournal(... COMPLETE)`, then `markMigrationCompleted(preferences)`, then rollback and journal cleanup. `markMigrationCompleted()` (`ExistingProfileMigrationService.kt:604-611`) uses `SharedPreferences.Editor.commit()` and throws on `false`, preventing cleanup after commit failure.

Recovery uses the same order (`ExistingProfileMigrationService.kt:665-685`): the `COMPLETE` branch commits first, deletes rollback and stage second, and reaches stable/temporary journal deletion only after the branch. Commit failure becomes `Blocked` while the `COMPLETE` journal remains for retry.

## Public recovery exception contract — prior issue 2 CLOSED

**CLOSED, confirmed:** `recoverInterruptedMigration()` (`ExistingProfileMigrationService.kt:619-643`) wraps mutex acquisition, `Dispatchers.IO`, `withCollectionClosedForRecovery`, and unlocked recovery in one outer `try`. ## Strict close retains failed handles — prior issue 3 CLOSED

**CLOSED, confirmed:** `ensureClosedForFilesystemRecovery()` (`CollectionManager.kt:249-253`) enters `withQueue` and invokes `ensureClosedStrictInner()`. The strict implementation (`CollectionManager.kt:299-305`) calls `current.close()` before `collection = null`; a thrown close propagates and skips reference clearing.

The post-activation catch calls this API whenever `stagingActivated` is true (`ExistingProfileMigrationService.kt:189-199`). A close failure is suppressed onto the original failure, while the retained live reference makes `withCollectionClosedForRecovery()` (`CollectionManager.kt:259-265`) fail its `collection?.dbClosed != false` guard before filesystem mutation.

## Activation-return cancellation cleanup — prior issue 4 CLOSED

**CLOSED, confirmed:** `activateCollectionDirectory(...)` is inside the `try` in `ExistingProfileMigrationService.activate()` (`ExistingProfileMigrationService.kt:157-200`). The activation lambda sets `stagingActivated = true` immediately after `rename(paths.staging, paths.target)`.

Cancellation delivered while the successful queue call returns is caught with `stagingActivated == true`. The catch runs `ensureClosedForFilesystemRecovery()` inside `withContext(NonCancellable)` and then rethrows the original cancellation.
