# Retained Expressive transfer pipeline with scoped export enforcement

Task 12 now centralizes export scope/format policy, moves provider I/O into retained coordinator ownership, persists only typed state and opaque file tokens, and adds strict collection transfer protocols plus focused contract tests. Seven of the prior nine findings are addressed, including canonical defaults, exact `ExportLimit` construction, provider-copy commit ordering, bounded staging cleanup, and non-cancellable post-replacement invalidation. Two destructive/replay boundaries remain incomplete: external import identities are regenerated rather than stable across redelivery, and collection replacement does not recover or type a failure when close partially succeeds before throwing. Watch for: **confirmed P1** a redelivered external intent can stage the same source again under a fresh identity; **confirmed P1** a partial replacement close failure can return with the collection closed, and a reopen failure after commit is flattened to a generic import failure.

**Verdict**: NEEDS_CHANGES

## High-level view

Export policy is now shared by the UI and gateway: COLPKG is accepted only for whole-collection scope, restored invalid combinations decode closed, and whole/deck/selection defaults match the required COLPKG/APKG mapping. APKG and text exports retain exact whole, deck, note-ID, or card-ID limits, so labels and backend scope agree.

Import staging and Create Document copying now enter explicit `CopyingImport` and `SavingExport` states before retained `viewModelScope` I/O. Saved snapshots omit provider names, URIs, and raw paths; app-owned artifacts are resolved from bounded opaque basenames under canonical import/export/selection roots, and save success is persisted before source deletion.

External import consumption is recorded before staging and restored active/terminal state is not overwritten. The identity is generated afresh in `IntentHandler.getExpressiveImportBootstrapIntent()` and replaced again by `ExpressiveHomeActivity.getExternalImportIntent()`, while the consumed set lives only in that Home activity's `SavedStateHandle`; a redelivery that creates a new routing/activity instance therefore appears to be a new request (**confirmed P1**).

COLPKG replacement now uses strict close and holds close, backend replacement, and reopen under the collection queue; export similarly attempts reopen after close/backend/cancellation failures. Replacement's strict helper calls `close()` outside its recovery guard, so a close that closes the database and then throws bypasses reopen, and a post-commit reopen failure is surfaced only as `IMPORT_FAILED` without the required typed recovery outcome (**confirmed P1**).

The focused suite exercises defaults, invalid pair rejection, exact limits, snapshot hygiene, canonical/symlink rejection, staging cleanup, stale result gating, provider-copy ordering, MIME grants, and basic close/reopen/cancellation contracts. It does not exercise stable external identity across separate redeliveries or replacement close/reopen failures after a partial close/committed backend mutation.

## External import identity changes at each routing boundary

**Confirmed P1.** `IntentHandler.getExpressiveImportBootstrapIntent()` assigns a random UUID whenever it handles an incoming VIEW/SEND intent. After the startup gate, `DeckPicker.launchPostStartupDestinationIfRequested()` calls `ExpressiveHomeActivity.getExternalImportIntent()`, which discards that UUID and assigns another random UUID. `startExternalImport()` persists and checks the final UUID before staging, but that UUID identifies one generated Home intent rather than the originating external request.

The consumed-ID list is stored in `ExpressiveTransferCoordinatorViewModel`'s `SavedStateHandle`. It protects recreation of the same Home activity, but `ExpressiveHomeActivity` has no single-task launch mode and a separately redelivered external intent can create a fresh bootstrap/Home instance with a fresh handle and fresh UUID. The same provider source can therefore be staged and imported again, contrary to the exact-once requirement. Generate one bounded deterministic digest/identity for the originating intent without storing raw URI text, preserve it through DeckPicker and Home, and persist the bounded consumed set in scope shared by redeliveries before staging.

The added tests verify that an ID is opaque and that the same coordinator rejects an already-consumed ID. Not tested: calling the routing entry point twice with the same external intent and proving both paths carry the same identity into independently created coordinators, with only one admitted to staging.

## Partial strict close has no replacement recovery path

**Confirmed P1.** `runStrictCollectionReplacementProtocol()` invokes `close()` before entering the `try/finally` that guarantees reopen. `ensureClosedStrictInner()` clears the manager's collection reference only after `current.close()` returns, so a close implementation that marks the database closed and then throws leaves a closed wrapper installed and returns without any reopen attempt. This is the partial-close case that `runFullCollectionExportProtocol()` explicitly handles with `isClosed()`, but replacement lacks the equivalent recovery check.

After backend replacement succeeds, an `ensureOpenInner()` failure is thrown from the helper. `DefaultExpressiveTransferGateway.replaceCollection()` consequently never publishes global invalidation, and the coordinator maps the outcome to generic `IMPORT_FAILED`; the collection files may already be replaced, but callers receive neither a usable collection nor a typed recovery failure. Guard the replacement close with state-aware recovery, distinguish committed replacement from reopen failure, and publish the required exactly-once invalidation while returning a dedicated recovery result when usability cannot be restored.

The new contract test only models a close that throws without becoming closed and asserts that reopen is not called. Not tested: close-then-throw recovery, backend-failure reopen, successful replacement followed by reopen failure, or the resulting typed recovery/invalidation behavior.
