# Fix pass on the Study screen's Material 3 Expressive chrome

This pass addresses the ten issues from the previous review. The toolbar and the ratings now share one row only in short windows that are at least 600 dp wide, and the bottom bar clears the keyboard as well as the navigation bar. The flag menu moves to M3E's grouped `DropdownMenuPopup` with selectable items. When the flag names can't be read, the flag button steps through the flags instead. All ten issues are resolved in code; the tests and ktlint ran after the last edit, and the screenshots before it.

**Watch for:**

- **Likely, should-fix:** moving the flag menu into `DropdownMenuPopup` drops the scrolling that `DropdownMenu` had. The eight-flag menu is about 390 dp tall at 1× and grows with the font size. From about 1.5× font scale, the last flags fall outside a landscape or split-screen phone window and can't be reached.
- **Likely, low:** in a landscape phone with the keyboard docked, the keyboard inset, the app bar, and the controls leave the type-answer field about 25 dp. This isn't a regression, because the keyboard used to cover the field, but the G1 device check should include it.

**Verdict**: NEEDS_CHANGES

## High-level view

`StudyLayout` puts the toolbar and the answers in one row only in windows under 480 dp tall and at least 600 dp wide. Its bottom bar pads for `navigationBars.union(ime)`. In portrait, that lifts the type-answer field above the keyboard. In a landscape phone, the same padding leaves the field almost no height.

The flag menu now tells TalkBack which flag is selected, through alpha18's selectable `DropdownMenuItem`. The `DropdownMenuPopup` it moved into doesn't scroll, though, unlike the `DropdownMenu` of the previous pass. At large font sizes, eight flags don't fit a short window.

### Flag menu on `DropdownMenuPopup` loses its scrolling

**Likely.** The missing scroll is confirmed in the alpha18 source; the overflow is calculated, not captured. Neither `DropdownMenuPopupContent` nor `DropdownMenuGroup` scrolls: both lay out their items in a plain `Column`. The `DropdownMenuContent` behind the previous pass's `DropdownMenu` applies `.verticalScroll(scrollState)`.

Each selectable item is 12 dp + label line + 12 dp, and at least 48 dp for touch. The group adds 2 dp above and below. With eight flags, the menu is about 388 dp at 1×, which matches the 390 dp in `study_flag_menu.png`. It is about 404 dp at 1.3×, 436 dp at 1.5×, and 516 dp at 2×.

A landscape phone window is about 411 dp tall, and the split-screen window is 415 dp. From about 1.5×, Purple falls outside the popup, and at 2× Turquoise does too. Neither touch nor TalkBack can scroll to them. The captures show the menu only on a portrait phone and on the tablet, so this case isn't recorded.

```kotlin
DropdownMenuGroup(
    shapes = MenuDefaults.groupShape(0, 1),
    // The group applies its modifier to its item column.
    modifier = Modifier.verticalScroll(rememberScrollState()),
) { /* … */ }
```

### Keyboard inset in a landscape phone

**Likely.** Take a 411 dp landscape window with the keyboard docked:

- The status bar, the app bar, and its wave take about 106 dp (82 dp in the capture, which has no status bar).
- The one-row bottom bar takes 80 dp plus the IME inset.
- A landscape keyboard is typically about 200 dp.

That leaves about 25 dp. The weighted `CardPane` gets nothing, and the `OutlinedTextField` is measured below its 56 dp minimum. The same squeeze applies to the WebView's own `<input>` on `typeUseInputTag` cards.

Before this pass, the keyboard covered the field in the same window, so this isn't a regression; the IME fix helps portrait phones only. The type-answer layout was deliberately left to the G1 device check, and that check should include landscape.

### The ten previous issues

1. **Row switch:** resolved. The condition is `maxHeight < 480.dp && maxWidth >= 600.dp`. Component tests cover 914 × 411 dp and 411 × 415 dp, and the split-screen capture shows the controls stacked.
2. **Keyboard:** resolved in code, apart from the landscape gap above.
3. **Disabled flag:** resolved with `alpha(0.38f)` on colored flags; the neutral flag dims through the `IconButton`. No capture shows a disabled toolbar.
4. **Selected flag:** resolved. The alpha18 source sets `Role.RadioButton` and uses `Surface(selected = …)`, and the test asserts both. The switch to `DropdownMenuPopup` caused issue 1.
5. **Flag-name failure:** resolved. Cancellation is rethrown. Other failures are logged with `Timber.w` and return an empty map, after which the button cycles in the same order as the gateway's gesture cycle. Three gateway tests and one component test cover this.
6. **Title:** resolved with `Decks.basename(deckName)`.
7. **One rating per row:** resolved. When `perRow == 1`, `labelMaxLines` is `Int.MAX_VALUE` and the text is centered. No test covers this case, which only occurs when a label is wider than half the row.
8. **Show answer disabled:** resolved. Its disabled colors are primary and on-primary. While it waits, it looks live but ignores taps, for at most the 15 s scheduling timeout.
9. **Tests:** resolved. A recording `HapticFeedback` covers the button and mark haptics. `GestureAnswerHapticTest` pins the gesture decision, whose guard matches `StudyViewModel.grade`. Other tests cover the row switch and flag-name loading. The `gradeByGesture` glue remains untested, and so, deliberately, does the type-answer layout.
10. **Screenshots:** resolved. The byte-identical tablet "land" captures are gone. Tablet portrait, phone split screen, and both menus are now captured: 30 PNGs from 36 cases, with 6 skipped by assumption. Dynamic color stays a G1 device check, as accepted in F1.

The full expressive suite (195 tests) last ran at 10:50, before the haptic and flag-name extraction. The 14:46 run recompiled the main and test source sets. It ran the three touched classes, 20, 16, and 2 tests, with no failures in the XML reports. No other test references `answerHaptic`, `gestureAnswerHaptic`, or `flagNamesOrNone`.
