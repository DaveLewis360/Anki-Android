# Native Expressive backup, restore, and collection maintenance

Task 13 adds a retained maintenance coordinator and a Compose Maintenance route for backups, retention, restore, database check, empty cards, and media, with no Classic fallback. A restore is imported by a separate backend into a sibling staging directory and validated before confirmation. A process-wide generation owns that staging, and a journaled rename swap activates it, rolls back unless the restored database opens, and resumes the media merge after process death. All backups share one mutex and await completion outside the collection queue; saved state is versioned and holds no paths or names. The swap holds up at every crash point I traced, but the promised safety backup can be silently skipped, restore artifacts can outlive their owner, and several edges lose data or feedback. **Watch for:** **likely P1** the forced safety backup's `false` result is ignored; **confirmed P2** orphaned staging is never swept; **likely P2** media that fails to merge is deleted with staging; **confirmed P2** a queued media sync suppresses automatic backups; **confirmed P2** retained work captures the Activity and does file/HTML work on Main; **likely P2** progress live regions flood TalkBack; **confirmed P2** an unused string fails the project lint gate; **confirmed P2** the failure boundaries are untested.

**Verdict**: NEEDS_CHANGES

## High-level view

Restore runs in three steps: prepare, confirm, commit. Preparation imports the COLPKG into `.<dir>.expressive-restore-stage` with a separate backend and opens it there, under `ExpressiveRestoreStaging`'s mutex and a fresh generation. Commit takes a forced backup, then swaps only the database files through a PARKING → PARKED → ACTIVATED → COMPLETE journal. The gap on this destructive path is the safety backup: `commitRestore` ignores the `Boolean` the backend returns. The backend returns `false`, without writing a file, when the open collection has not changed since its last backup attempt (**likely P1**).

The journal itself is sound. Moves are rename-only, recovery runs in `ensureOpenInner` before any closed collection opens, and rollback deletes the restored database's sidecars so its WAL can never be replayed into the previous database. The risk is in what the journal does not own. Recovery ignores staging that has no journal, and only an explicit discard or restored-state cleanup removes it (**confirmed P2**). After COMPLETE, a media file that fails to rename is only counted, and the staging that still holds it is then deleted (**likely P2**).

Automatic backups are attempted on every resume, but their sync gate uses `isActive`, which includes `MediaQueued`. With the "only unmetered" media policy, a media job waiting for Wi-Fi therefore suppresses automatic backups, and refuses database and restore work, for as long as the device stays on metered networks (**confirmed P2**).

The Activity passes itself into the retained coordinator as `Context`, and coroutines that can run for minutes capture it. The same coroutines unlink multi-gigabyte cache files and parse an unbounded HTML report on the main thread (**confirmed P2**).

On the screen, the accessibility gap is in announcements. Progress text that changes every 250 ms sits in a polite live region, and a database check that fixed problems finishes with no announced summary (**likely P2**). One new string is never referenced, and the project's lint config treats `UnusedResources` as fatal (**confirmed P2**). The tests pin the happy paths, stale generations, and three crash points, but none of the failure boundaries above (**confirmed P2**).

1. **Likely P1 — Safety backup result ignored** — `commitRestore()` proceeds when `createBackup(force = true)` returns `false`. 3. **Likely P2 — Unmerged media deleted** — `mergeRestoredMedia()` counts rename failures, `finishCompletedExpressiveRestore()` then deletes staging, and the restore reports success. Keep unmerged files recoverable (bounded retry or a quarantine folder) and surface a partial-media result.

## Forced safety backup trusts a result it never reads

**Likely P1.** `DefaultExpressiveMaintenanceGateway.commitRestore()` (`ExpressiveMaintenanceCoordinator.kt:373-389`) treats any non-throwing return from the forced backup as success:

```kotlin
try {
    createBackup(force = true)   // Boolean discarded
} catch (failure: Exception) {
    throw SafetyBackupException(failure)
}
ExpressiveRestoreStaging.commit(generation)
```

Anki's `create_backup` contract says a forced backup may return `false` when the collection has not changed since the last backup. The backend makes that comparison against an in-memory timestamp, which it records when the backup starts; the worker thread receives only the copied bytes, the folder, and the limits, so it cannot record the outcome. A `false` result therefore does not prove that any backup file exists.

Two reachable sequences replace the collection with no copy of it. In the first, an automatic backup fails: `awaitBackupCompletion()` consumes its error and the coordinator only logs it (`:603-610`), and the user then restores without editing anything. In the second, the user deletes the newest backup through DELETE_BACKUP and then restores an older one. In both cases the confirmation text (`02-strings.xml:547`) has already promised a new backup of the current collection. Manual CREATE_BACKUP has the same root cause: it reports "Backup created." for a `false` result, as Classic does.

Accept `false` only when the newest resolvable backup is at least as new as `col.mod`, the value the backend compares. Otherwise write a non-deduplicated safety copy, or fail closed with `SafetyBackupException`. Add gateway tests that restore after deleting the newest backup, and after a failed previous backup.

## What the restore journal does not own

```
prepare (staging mutex, separate backend)       commit (staging mutex, then collection queue)
  settle journal, rm stage, import, open          safety backup, validate stage, strict close
  generation N owns ...expressive-restore-stage   PARKING    move live DB files to -rollback
                                                  PARKED     move staged DB files in
ensureOpenInner (closed collection only)          ACTIVATED  open the restored DB
  COMPLETE -> finish merge and cleanup            COMPLETE   merge media, rm rollback/stage/journal
  otherwise -> roll back
```

**Confirmed P2 — orphaned staging.** Only five paths delete staging: `prepare` (before re-creating it), `discard`, a failed commit, rollback, and finish. After process death, the coordinator calls `discard(null)` only if the restored saved state is an interrupted PREPARE_RESTORE or RESTORE (`ExpressiveMaintenanceCoordinator.kt:957-973`), and it has no `onCleared()`. Recovery in `ensureOpenInner` acts only on journals (`CollectionManager.kt:572-580`, `:751`).

Staging is therefore left behind when the Activity finishes while ConfirmRestore is shown (for example, the task is swiped away), when the app crashes, or when the process dies and its saved state is not restored. What stays is the imported database plus every media file extracted from the package. It sits beside the collection directory, outside the OS-reclaimable cache, until the user starts another restore. Because `preparedGeneration` lives in process memory, any staging that exists without a journal before a process's first preparation must be orphaned. Sweep it under `ExpressiveRestoreStaging.mutex` at the first settle or open. Also discard owned staging from `onCleared()` in a non-cancellable, process-scoped job.

## Media merge discards what it cannot move

**Likely P2.** After COMPLETE, `mergeRestoredMedia()` renames staged files into `collection.media` and only counts failures (`CollectionManager.kt:629-640`). `finishCompletedExpressiveRestore()` then deletes staging, rollback, and the journal (`:615-626`), and the coordinator reports "Your collection was restored." A file whose rename failed is gone, even though the restored database references it. This is most likely on a nearly full device, where the parked old database, the restored database, and the extracted media all exist at the moment the live media directory has to grow. A folder-creation failure, by contrast, throws and is retried from the retained journal.

Keep unmerged files, either in staging with a bounded retry or in a quarantine folder, and surface a partial-media result. The retry must be bounded. While a COMPLETE journal remains, `settleExpressiveRestore()` returns `false` and every later preparation fails.

## Automatic backups gated on media queue state

**Confirmed P2.** The Activity starts automatic backups only when `!syncState.isActive` (`ExpressiveHomeActivity.kt:377-381`). The coordinator rechecks the same predicate through `isSyncActive` (`:316`; `ExpressiveMaintenanceCoordinator.kt:603`). `isActive` includes `MediaQueued` (`ExpressiveSyncViewModel.kt:304-307`). Under the "only unmetered" policy, the media request carries an `UNMETERED` constraint (`SyncMediaWorker.kt:160-161`), so after any sync on mobile data it stays enqueued until Wi-Fi returns. No automatic backup runs for that whole interval, even though backups read only the collection database and a queued media job touches nothing. The same predicate refuses database check and restore with "Wait until sync has finished" while nothing is running.

Gate automatic backups on collection-sync ownership (`isCollectionBlocking`). Keep the media-phase exclusion for media and restore work, and tell the user when the blocker is a media job waiting for an unmetered network.

## Retained coroutines hold the Activity and do I/O on Main

**Confirmed P2.** The Activity passes itself as `Context` to `stageExternalRestore`, `cleanupInterruptedArtifacts`, `open`, `confirmRestore`, and `back` (`ExpressiveHomeActivity.kt:152, 317, 374, 433, 526`). The coordinator captures that context in `viewModelScope` jobs that can run for minutes: a provider copy of up to 4 GiB followed by isolated validation (`ExpressiveMaintenanceCoordinator.kt:752-778`), and the restore itself (`:807-839`). Rotating the device during either job leaks the destroyed Activity until the job ends.

The same jobs run on `Dispatchers.Main.immediate`. `deletePendingImport()` unlinks the staged COLPKG synchronously (`:1081-1088`, called from `:820`, `:969`, and `:1077`). `findEmptyCards()` parses the whole backend HTML report with `HtmlCompat` before truncating it (`:882`, `:1146-1151`).

Convert to `applicationContext` at the coordinator boundary. The URI grant is checked against the app's UID, so the application context's resolver can still read the picked document. Then move file deletion and report parsing to `Dispatchers.IO` or `Default`.

## Live-region progress and an unused string

**Likely P2 — announcements.** `StatusText` puts every status in a polite live region (`MaintenanceScreen.kt:418-420`), and the running view renders the poller's text there (`:139-142`). The poller republishes backend progress every 250 ms (`ExpressiveMaintenanceCoordinator.kt:1032-1046`), so TalkBack announces each counter step of a long database or media check.

When a database check fixes problems, completion has no summary. `successText()` returns `null` whenever messages exist, and the messages render as plain `Text` (`MaintenanceScreen.kt:395-404`, `:478`), so the result goes unannounced. The counter is also built as `"$stage $current/$total"` (`ExpressiveMaintenanceCoordinator.kt:441-443`) rather than taken from a string resource.

Keep the live region on the stage label and terminal summaries, and render counters without it. For results that have messages, announce a summary such as a plural "N problems fixed".

**Confirmed P2 — lint.** Nothing references `expressive_maintenance_media_trash_restored` (`02-strings.xml:571`); RESTORE_MEDIA_TRASH uses `TR.mediaCheckTrashRestored()` instead. `lint-release.xml:30` makes `UnusedResources` fatal, and `lint.gradle:10` applies that config with `abortOnError`, so `lintFullDebug` and `lintAll` fail. The reported validation ran ktlint but not Android lint.

## Tests pin the happy paths, not the failure boundaries

**Confirmed P2.** The gateway suite runs the real backend through restore, media merge, three crash points, stale generations, and each maintenance operation. The coordinator suite pins admission, no-replay, saved-state hygiene, and late-result suppression. Not tested: a `false` or failing safety backup; rollback failure and the retry from the retained journal; a crash during PARKING or partway through PARKED; resuming an interrupted media merge (the COMPLETE crash test has no media); journal-less staging after process death; and the Activity wiring (automatic backup on resume, back during an admitted operation, picker routing, and `requestSync()` refusal).

I did not run Gradle, lint, or tests. The forced-backup semantics come from Anki's documented `create_backup` contract, because no `rslib` source is available locally. I did not verify directory `fsync` behaviour on FUSE-backed storage. I also did not verify whether Classic startup-sync media work (unique `SYNC_MEDIA`) can still be running after the Expressive handoff; `isSyncActive()` sees only the Expressive attempt record.
