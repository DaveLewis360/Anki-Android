# A design-system layer for Expressive menus and medium buttons

The Study screen's three menus and its medium buttons (Show answer, the ratings, the panes' first button) now go through the new `ui/expressive/designsystem` package, so the alpha18 menu and button-size APIs are called in one place. `ExpressiveMenu` builds grouped `DropdownMenuPopup` menus from lists of items, closes before it runs the chosen item, and scrolls either inside a lone group or around several; `MediumButton` wraps the 56 dp Expressive `Button` with its matching shape and padding, and in its label overload the matching text style. The long-press menu now takes `expanded` and stays composed, so it animates out like the toolbar menus. Moving the scroll state and the scroll container into the shared menu changed two things users can see.

Watch for: the menus' `ScrollState` now lives outside the popup, so the flag and long-press menus reopen where they were last scrolled instead of at the top (confirmed); the more-card-actions menu now sits in a vertical scroll whose clip cuts the shadow above its first group and below its last on devices, which Robolectric screenshots cannot show (confirmed); `MediumButton`'s content overload leaves its content at the default label style, not the larger one its KDoc promises (confirmed); the plan strikes the "alpha API changes land in one place" step as done while `ButtonGroup`, `HorizontalFloatingToolbar`, `SegmentedListItem` and `LoadingIndicator` are still called directly (confirmed). The first two are the reason for the verdict.

**Verdict**: NEEDS_CHANGES

## High-level view

`ExpressiveMenu` maps each inner list to a `DropdownMenuGroup` with `MenuDefaults.groupShape`, gives items `MenuDefaults.itemShape`, and picks the action overload (`Role.Button`) for `selected = null` or the radio overload (`Role.RadioButton` plus selected state) for a Boolean, an API no larger than its three users need. Checked against HEAD and the alpha18 sources: flag items still read as radio buttons with the set flag selected, bury, suspend and long-press items as buttons, every menu still dismisses before it acts, and `MediumButton` passes the same height, shapes, padding, colors (disabled ones included) and content descriptions; Show answer's newly centered label is the sub-pixel shift in study_question.

Remembering the one `ScrollState` in `ExpressiveMenu` rather than inside the popup lets it outlive the menu: the flag menu and the now always-composed long-press menu reopen at their last offset instead of the top, which shows whenever a menu is taller than its window.

For several groups the scroll wraps all of them, and a vertical scroll clips at its top and bottom edges. The groups' 3 dp shadows fall outside that clip, so the more-card-actions menu loses the shadow above Bury and below Suspend in every window, overflowing or not, and the Roborazzi compare cannot see it.

The always-composed long-press menu keeps its anchor, the card area's unkeyed `Box`, so its exit animation survives the card change that Bury, Suspend and Undo cause. StudyScreen dropped its own `gestureMenu = false` and relies on `ExpressiveMenu` calling `onDismissRequest` first; no test holds that contract.

The Home deck menu, F3's first user, is plain actions and fits the item model; grouped, it inherits the shadow clip. `MediumButton`'s content overload, the one an icon-and-label button would use, sets the medium height, shape and padding but not the medium text style, so such a caller would call `ButtonDefaults.textStyleFor` itself again. The plan's F2E entry is accurate; its section 4 strikes the layer requirement as done.

### Scroll offset outlives the menu

(confirmed) At HEAD the flag and long-press menus remembered their scroll state inside the popup content:

```kotlin
DropdownMenuPopup(expanded = flagMenu, onDismissRequest = { flagMenu = false }) {
    // composed only while the menu is open or animating
    DropdownMenuGroup(shapes = …, modifier = Modifier.verticalScroll(rememberScrollState())) { … }
}
```

`ExpressiveMenu.kt:44-55` remembers it in the caller's composition instead:

```kotlin
val scroll = rememberScrollState()
DropdownMenuPopup(expanded = expanded, …) {
    DropdownMenuGroup(…, modifier = if (scrollsWithinGroup) Modifier.verticalScroll(scroll) else Modifier)
}
```

`DropdownMenuPopup` composes its content only while `expandedState.currentState || expandedState.targetState` (Menu.kt:247), so the old state was forgotten on every close. The new one lives as long as `ExpressiveMenu` is composed: across cards for the flag menu in `StudyCardActions`, and for the whole session for the long-press menu, now that StudyScreen no longer wraps it in `if (gestureMenu)`; being saveable, it also survives rotation. In the landscape 2× configuration of study_flag_menu_land_font_2x, choosing Purple leaves the next card's flag menu open at the bottom with No flag and Red scrolled out of view, and choosing Undo from the long-press menu hides Flag the next time. M3's own `DropdownMenu` keeps its default `ScrollState` the same way, so this is a choice, but not what these menus did before F2E, which the change set out to keep. Remembering the state inside the popup content restores it; for several groups that means scrolling an inner `Column` within the popup rather than the popup's own modifier, which is also where the shadow fix below would go.

### Two groups: the scroll clip cuts the outer shadows

(confirmed by code; not verified on a device) For several groups `ExpressiveMenu` passes `modifier.verticalScroll(scroll)` to `DropdownMenuPopup`, which puts it in front of the popup column (`modifier.width(IntrinsicSize.Max).graphicsLayer { … }`, Menu.kt:1281). In foundation 1.11.3 (the BOM's version; `~/.cache/ankidroid-m3e/foundation/classes.jar` is that jar), `verticalScroll` goes through `scrollableArea`, which applies `clipScrollableContainer(Vertical)`; its `VerticalScrollableClipShape` is `Rect(-30.dp, 0, width + 30.dp, height)`, sparing shadows sideways but not above or below.

```
popup window (PopupLayout: clipChildren = false, elevation set, so shadows have room)
└─ Column  ← verticalScroll clip: top = 0, bottom = height
   ├─ DropdownMenuGroup  Bury card / Bury note         shadow 3 dp ← clipped above
   ├─ Spacer(MenuDefaults.GroupSpacing)
   └─ DropdownMenuGroup  Suspend card / Suspend note   shadow 3 dp ← clipped below
```

`DropdownMenuGroup` defaults to `shadowElevation = MenuDefaults.ShadowElevation` (`MenuTokens.ContainerElevation`, Level2, 3 dp), drawn outside its Surface. At HEAD the more menu's popup column had no clip, and the single-group menus still clip inside their Surface, so only the multi-group path loses the shadow, and in every window, because the clip does not depend on overflow. study_more_card_actions.png shows no shadow on either group: Robolectric draws no elevation shadows here, which is why the compare came back identical. Vertical padding inside the scroll, at least the groups' shadow extent, brings the shadows back inside the clip, at the cost of moving the groups that much farther from the anchor.

### `MediumButton`'s content overload and its KDoc

(confirmed) The KDoc on the content overload promises "a larger label", but the Expressive `Button(shapes = …)` wraps its content in `ProvideContentColorTextStyle(textStyle = MaterialTheme.typography.labelLarge)` (Button.kt:272-274); only the label overload sets `ButtonDefaults.textStyleFor(MediumContainerHeight)`, which is `titleMedium`. Today's content user, `AnswerButton`, styles its own texts, so nothing on screen changes. A Home "Study" button with an icon and a label would get 14 sp text unless it calls `textStyleFor`, and for the icon `contentPaddingFor(…, hasStartIcon = true)`, both `@ExperimentalMaterial3ExpressiveApi` calls the layer exists to hold. Providing the medium text style around `content` (explicit styles, as in `AnswerButton`, still win) or limiting the KDoc to the label overload fixes the mismatch.

### The plan strikes the layer requirement as done

(confirmed) Section 4's third mandatory step, "vékony design-system réteg (`ui/expressive/designsystem`), hogy az alpha API-változások egy helyen csapódjanak le", is now struck through like the two finished steps, with a note that the layer started and grows per screen. What sits in one place is what the F2E entry says, menus and button sizes: `DropdownMenuPopup`, `DropdownMenuGroup`, `MenuDefaults`, `shapesFor`, `contentPaddingFor`, `textStyleFor` and `MediumContainerHeight` appear nowhere else. Still called directly are `ButtonGroup` and `HorizontalFloatingToolbar` (StudyComponents.kt:518, 310) and `SegmentedListItem` (StudyPanes.kt:230), the APIs the option-B row says graduate in alpha22 and alpha23, plus ten `LoadingIndicator` calls in seven files and seven `ButtonDefaults.shapes()`. A reader of section 4 would expect the B migration to land in one package.

### Test coverage

The existing tests still hold the flag menu's radio role and selected state, its scroll to Purple in a 914×411 dp window at 2× font, the long-press menu's button role and scroll to Undo in the same window, and bury and suspend behind the more button. Not tested: that choosing an item calls `onDismissRequest` before the item's action, although StudyScreen now depends on it to close the long-press menu (the `GestureActionMenu` test passes `onDismiss = {}`, and no flag or more-menu test checks that the popup is gone); the two-group menu in a short window, whose scrolling is new; reopening a scrolled menu, which would have caught the retained offset. `designsystem` has no tests of its own.
