# Expressive startup handoff gated on foreground collection sync

The change adds an explicit classic-versus-Expressive startup destination and holds the Expressive handoff behind DeckPicker startup, foreground collection sync, and scheduler-v2 gates. Collection sync now distinguishes completed outcomes from a full-sync conflict that still needs user resolution, allowing `NO_CHANGES`, full upload, full download, and successful conflict resolution to release the handoff. The outcome mapping is sound, but the lifecycle state is neither scoped to a particular sync attempt nor able to distinguish an in-flight attempt from a failed or cancelled one. **Watch for:** **high, confirmed** stale foreground-sync completion can release a newer login request; **medium, confirmed** saved-state recreation retries failed/cancelled/conflicted requests; **medium, confirmed** post-sync exceptions or cancellation still call the completion hook; **low, confirmed** the tests bypass the production outcome machinery and omit the lifecycle races.

**Verdict**: NEEDS_CHANGES

## High-level view

The intended state machine is `startup complete + sync complete + scheduler v2 -> Expressive`, with classic startup retaining its existing automatic-sync path. Explicit Expressive login starts blocked, `FULL_SYNC` remains blocked until the selected upload/download succeeds, and scheduler v1 remains blocked until the upgrade callback reevaluates the destination.

The completion signal is activity-wide rather than attempt-specific. **High, confirmed:** after `onNewIntent` marks a new Expressive login pending, any older foreground sync that finishes can clear that pending flag and launch Expressive before the newly requested login sync succeeds.

Only three booleans survive recreation. **Medium, confirmed:** `loginStartupSyncPending` is restored and immediately converted back into `syncOnResume`, so rotation after conflict, auth failure, exception, missing auth, metered-prompt cancellation, or user cancellation silently retries the login sync and can duplicate collection work or prompts.

Sync outcome assignment excludes `FULL_SYNC` and failures, but completion is invoked from a `finally` around cache/subscriber/UI refresh. **Medium, confirmed:** an exception or cancellation after the backend returned a completed outcome still clears the login gate and can hand off despite the failed foreground-sync coroutine.

## Introduction login through Expressive handoff

The destination extra is copied through Introduction and returned when login opens DeckPicker with `INTENT_SYNC_FROM_LOGIN`. Within the reviewed files, that produces this state machine:

```text
Introduction login
       |
       v
DeckPicker(EXPRESSIVE + SYNC_FROM_LOGIN)
       |
       +--> startup fatal/permission/startup screens ----> blocked
       |
       +--> startup gate passed
                |
                +--> login sync pending -----------------> blocked
                |        |
                |        +--> NO_CHANGES ----------------> sync complete
                |        +--> FULL_UPLOAD/DOWNLOAD ------> sync complete
                |        +--> FULL_SYNC prompt ----------> blocked
                |        |        |
                |        |        +--> chosen full sync succeeds
                |        |                    |
                |        |                    v
                |        +--> auth/error/cancel/no auth -> blocked
                |
                +--> scheduler v1 -----------------------> blocked
                |        |
                |        +--> upgrade succeeds ----------> reevaluate
                |
                +--> scheduler v2 + sync complete -------> Expressive
```

`DeckPicker.kt:1805-1810` sends Expressive startup directly to reevaluation. `DeckPicker.kt:1817-1862` checks the startup, login-sync, scheduler, and handled gates and sets the handled bit before starting `ExpressiveHomeActivity`, preventing duplicate handoffs within one activity instance. Scheduler v1 is checked at `DeckPicker.kt:1828-1833`, with successful upgrade reevaluation at `DeckPicker.kt:783`. Absent or invalid destinations default to `CLASSIC` at `DeckPicker.kt:2490-2524`, and classic startup retains the pre-existing `automaticSync()` and backup-prompt path at `DeckPicker.kt:1805-1815`.

## A stale sync can satisfy a newer login intent

**High, confirmed:** the handoff completion has no request identity. `DeckPicker.kt:2530-2535` marks a new Expressive login pending and schedules its sync for resume. `DeckPicker.kt:1836-1843` accepts completion from any foreground sync whenever that boolean is true, while `Sync.kt:133-136` supplies no generation, auth identity, or attempt token.

```text
old manual/automatic foreground sync starts
new EXPRESSIVE + SYNC_FROM_LOGIN arrives in onNewIntent
loginStartupSyncPending = true
old sync completes and calls onForegroundSyncCompleted()
pending becomes false; Expressive launches
new login-requested sync has not succeeded and may never start
```

An older sync created with the previous `SyncAuth` can therefore satisfy the gate established by a later login intent. Associate the pending destination with a monotonically increasing attempt token or retained job/result, and only let matching completion release it.

## Recreation retries terminally blocked attempts

**Medium, confirmed:** the persisted state cannot represent why a login sync is pending. `DeckPicker.kt:501-505` restores `loginStartupSyncPending`, `DeckPicker.kt:527-530` turns every restored pending state into `syncOnResume = true`, and `DeckPicker.kt:1529-1531` saves no phase such as not-started, running, awaiting-conflict, failed, or cancelled.

Recreation after `FULL_SYNC` can consequently launch another normal sync while the restored conflict dialog awaits a choice. The same retry occurs after missing auth, auth failure, backend exception, coroutine/user cancellation, and metered-prompt cancellation. Persist or retain an explicit attempt phase, retry only a phase interrupted in flight, and leave terminal blocked phases inert until deliberate user action starts another attempt.

## Completed outcomes release when post-sync finalization fails

`Sync.kt:112-126` assigns `COMPLETED` after `NO_CHANGES`, full upload, full download, or selected conflict resolution returns successfully; `FULL_SYNC` returns `AWAITING_CONFLICT_RESOLUTION` at `Sync.kt:222-226`. Auth failure and operation exceptions leave before completion, missing auth returns before the coroutine, and declining the metered prompt never enters `handleNewSync`.

**Medium, confirmed:** `Sync.kt:129-136` places `onForegroundSyncCompleted()` in a `finally` around note-type cache clearing, subscriber notification, and `refreshState()`. An exception or cancellation in that block still clears the pending flag and schedules Expressive. Move completion after successful required finalization, or explicitly define and test which finalization failures are safe to ignore.

## Tests exercise booleans instead of sync outcomes

**Low, confirmed:** the new tests cover initial blocking, manually signalled success, repeated manual completion, classic routing, and scheduler-v1 blocking, but `LoginSyncDeckPicker` overrides `sync()` with a counter and directly exposes `onForegroundSyncCompleted()` (`DeckPickerTest.kt:1111-1123`). No added test drives `handleNewSync` through `NO_CHANGES`, one-way sync, conflict and resolution, auth failure, exception, or cancellation; none covers `onNewIntent` or recreation. Add production-path outcome tests plus recreation and overlapping-attempt tests.

The targeted new DeckPicker tests passed under `:AnkiDroid:testPlayDebugUnitTest`, and `git diff --check` passed. The full `DeckPickerTest` class had three failures involving `StorageNotConfiguredException` and an uninitialized `floatingActionMenu` in an unrelated recreation path; the broader uncommitted worktree prevented attributing those failures to this three-file diff.
