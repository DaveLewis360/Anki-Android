# Classic-profile migration recovery and startup gating

Task 4 adds a source-preserving Classic-profile copy into the Expressive app-owned collection directory, validates the staged payload, atomically activates it under the collection queue, and gates DeckPicker startup on interrupted-migration recovery. The artifact-ownership, Android storage-permission, and landscape findings are closed; atomic journal replacement is fixed, but its recovery finding remains partly open; the lifecycle finding also remains partly open. A torn temporary journal can permanently block startup despite a valid stable journal, recovery can mutate migration paths concurrently with activation, and the Activity still consumes cancellation as a normal failure. Watch for: **P1, confirmed** valid-journal recovery is blocked by a malformed `.tmp`; **P1, likely** recovery can race activation and discard the validated target while migration reports success; **P2, confirmed** Activity cancellation is swallowed.

**Verdict**: NEEDS_CHANGES

## High-level view

Journal updates now fsync `.tmp`, atomically rename it over the stable journal, and fsync the parent. Recovery promotes a valid matching `.tmp`, but parses `.tmp` before the stable journal, so a crash during temporary-file writing makes recovery retry an unrecoverable parse even when the previous stable journal is sufficient.

Migration attempts are serialized by a process-wide mutex and collection activation is serialized by `CollectionManager`. Recovery participates in neither boundary; another recovery Activity can roll back or delete journal, staging, rollback, and target paths while activation owns them.

API 24–29 request the manifest-declared `WRITE_EXTERNAL_STORAGE` permission, while API 30+ proceeds only to explicit source-readability checks. Deterministic artifacts are refused without matching journal ownership, and the landscape introduction stacks all three actions vertically.

The service rethrows `CancellationException` after cleanup, but the Activity wraps the call in `runCatching` and converts cancellation into `MigrationUiState.Failed`. Orientation and screen-size handling reduce recreation, but do not preserve cancellation for back navigation, other configuration changes, or destruction.

## A torn `.tmp` overrides a usable stable journal

**P1, confirmed:** `writeJournal()` opens the deterministic temporary file, writes and fsyncs it, then atomically renames it over the stable journal (`ExistingProfileMigrationService.kt:456-484`). Process death during the write can leave the previous valid journal plus a truncated `.tmp`, which is the crash-safe fallback the stable journal is meant to provide.

Recovery calls `promoteTemporaryJournal()` before reading the stable journal (`ExistingProfileMigrationService.kt:583-592`). Promotion unconditionally decodes `.tmp` and throws on malformed content (`ExistingProfileMigrationService.kt:627-634`); the outer catch returns `Blocked` (`ExistingProfileMigrationService.kt:619-624`). DeckPicker sees either journal file and routes back to recovery before collection startup (`DeckPicker.kt:504-513`), so retry repeats the same parse forever. Parse and validate both candidates independently, promoting a valid matching `.tmp` but falling back to a valid matching stable journal.

## Recovery bypasses the migration and collection serialization boundaries

**P1, likely:** `migrate()` holds `migrationMutex` only around `migrateBlocking()` (`ExistingProfileMigrationService.kt:58-69`), while companion recovery mutates journal, staging, rollback, and target paths without that mutex (`ExistingProfileMigrationService.kt:583-618`). `ExistingProfileMigrationActivity.recoverAndContinue()` calls the unsynchronized function directly on `Dispatchers.IO` (`ExistingProfileMigrationActivity.kt:134-147`). The collection queue excludes collection operations, not this recovery coroutine.

After activation writes `TARGET_PARKED` and renames stage to target (`ExistingProfileMigrationService.kt:154-157`), recovery can read `TARGET_PARKED`, move the activated target back to stage, restore rollback, delete stage, and delete the journal (`ExistingProfileMigrationService.kt:598-618,643-649`). Activation can then open the restored pristine target, write `COMPLETE`, and return success after recovery discarded the validated copy. Recovery needs the same process-wide serialization for its full inspect/rollback/delete transaction and exclusion from collection activation.

## Lifecycle cancellation is still converted into an ordinary failure

**P2, confirmed:** the service catches `CancellationException`, cleans incomplete COPY/READY state, and rethrows (`ExistingProfileMigrationService.kt:121-124`). `ExistingProfileMigrationActivity.startMigration()` catches every throwable with `runCatching` and folds cancellation into `MigrationUiState.Failed` (`ExistingProfileMigrationActivity.kt:108-130`). The manifest handles orientation and `screenSize` (`AndroidManifest.xml:502-504`), but back navigation, other configuration changes, or destruction can still cancel `lifecycleScope` without cancellation propagating through the Activity job.

If cancellation is delivered after non-suspending activation commits, the target can be valid and the journal gone while Introduction receives no success result; retry is then refused as non-pristine. Rethrow `CancellationException` before mapping operational exceptions and prevent the result contract from being abandoned mid-commit.
