# Anki night-mode classes for Study cards, with card motion gated on page commit

The Study screen no longer forces colors on card templates. `expressiveCardHtml` rewrites the renderer's `<body class>` so Anki's night-mode classes match the Expressive theme. In dark mode it paints the canvas through flashcard.css's own `body.night_mode` selector, from a `<style>` placed after flashcard.css and before the note type's CSS. The in-document keyframes are replaced by a Compose `CardMotion` on the pane's `graphicsLayer`. It fades the previous document out when a render starts and slides or rises the next one in once `onPageCommitVisible` (or `onPageFinished`) reports it drawable. If neither arrives within 1.5 s, it shows the pane anyway. The 174 `com.ichi2.anki.ui.expressive.*` tests pass (0 failures), in a run that started after the last edit.

**Watch for:** **likely:** the answer side settles without waiting for the gate. A reveal that lands before the question commits therefore fades the previous card's answer back in. **likely:** with system animations off, the leave blanks the pane at once, so every new question flashes empty until it commits. Nits (confirmed): `ankidroid_plain_mode` survives into dark pages, the unconditional `img{max-width:100%}` was dropped without mention, and the KDoc and a test name overstate why note-type rules win.

**Verdict**: NEEDS_CHANGES

## High-level view

Theming now follows Anki's model instead of overriding it. The body carries `night_mode nightMode ankidroid_dark_mode` exactly when the Expressive background is dark. This also fixes `.nightMode .latex` inversion and the replay-button fill, which used to follow the stale Classic theme. The dark rule has the same specificity as flashcard.css's and comes later. Note-type CSS therefore wins or loses against it exactly as it does against flashcard.css in Classic. Light mode sets no colors, so a stock note type's white `.card` now shows as a white panel between 20 dp gutters of the M3 background, which may be wallpaper-tinted. The light-mode test asserts this deliberately.

Motion moved out of the document and into the pane. On the question side the pane is hidden while the page loads and enters on commit. After 1.5 s it fails open and shows whatever the WebView still draws. The answer path skips the gate and swaps documents in place, and that is where stale content leaks through. Reading the Animatables inside `graphicsLayer` keeps motion out of recomposition. The themed HTML is now `remember`ed instead of rebuilt on every recomposition.

`onPageCommitVisible` reuses the token-URL and `started` guards from `onPageFinished`, and it only feeds `visibleRenderKey`. `readyRender`, which authorizes internal navigation, is still set only on `onPageFinished`. A page that is visible but not yet finished therefore can't issue commands.

### Leave, enter, and fallback in `CardPane`

The Question and Answered branches each compose their own `CardPane`, and the two share one `CardMotion`. Each pane runs an effect keyed on `(renderKey, visible)`. These orderings were traced: a commit mid-leave, a late commit from the previous document, and a reveal mid-enter. Only the answer path shows stale content. **Likely:** it happens whenever the back-side render finishes before the question commits:

```
Question(N) composed  → leave: alpha → 0        WebView still draws A(N-1)
render(Q(N)) begins                             Q(N) not committed yet
reveal → Answered(N)  → question pane disposed, leave cancelled
                      → side == ANSWER → settle: alpha → 1   ← A(N-1) fades back in
render(A(N))          → stopLoading() aborts Q(N)
A(N) commits          → swaps in place
```

The window runs from `working` clearing until Q(N) commits. A fast reveal after grading can hit it, whether from a gesture, the button, or a keyboard shortcut. Two refresh paths emit `Question` and then `Answered` back to back and take the same branch: `refreshAfterNoteEditor` and the debounced external reload. In those cases the stale document is the same card's pre-refresh answer.

**Likely:** with animations off, `Animatable.animateTo` completes on its first frame, but `delay(1_500)` isn't scaled. Every new question is therefore a hard cut to the empty pane (the Compose background), then back when the page commits. The KDoc's "every step completes at once" is accurate, and this is what it looks like on screen.

The fallback fails open by design. Without a commit within 1.5 s, `settle` reveals whatever the WebView still draws, which is the previous card. When the commit finally arrives, the offset snaps at full alpha.

### Parity with flashcard.css

The theme's `body.night_mode,body.ankidroid_dark_mode` (0,1,1) has the same specificity as flashcard.css's rules and comes after them. The M3 background and `onBackground` therefore replace flashcard.css's black/#303030 background and white text. Note-type CSS in `#qa` comes later still. `body.nightMode {…}` wins the tie by order, and `.card.night_mode {…}` (0,2,0) wins outright. Bare `.nightMode {…}` and the stock `.card` colors lose, exactly as they lose to flashcard.css in the Classic reviewer. The class rewrite strips only the three night classes, so `ankidroid_plain_mode` survives (issue 3). `:root{color-scheme}` is the one thing Classic doesn't set, and it only changes UA-styled controls and scrollbars.

### Test coverage

`ExpressiveCardHtmlTest` (5 tests) covers the light and dark class rewrites, the rule text, insertion order, typeans hiding, and the fragment fallback. The new `ExpressiveCardWebViewTest` case covers stale-URL, pre-start, and duplicate commits. Not tested: the CardPane state machine (including reveal before commit), the `onPageFinished` visibility fallback, the animations-off path, renderer theme classes other than the night ones, and any real cascade outcome. No device run is reported. The removed KDoc blamed container-level animation for glitches, so a device pass is the check that matters.
