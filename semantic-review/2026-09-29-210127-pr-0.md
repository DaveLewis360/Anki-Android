## High-level view

`Themes.setTheme` is safe in this host. It runs before the decor view exists, so the debug fail-fast can't trip. Without a manifest theme the base is the application's `Theme_Light`, so the launcher-splash branch isn't taken. AppCompat's night-mode configuration override, which a FragmentActivity doesn't get, only matters for night-qualified resources, and here those are just the flag colors. The call also refreshes the global `Themes.currentTheme` that PageFragment reads for `#night`. The Expressive screens write the classic prefs through `syncToClassicThemePrefs` but never update that global, so before this fix a mid-session theme change never reached the import page. The one part of AnkiActivity's theming the host doesn't copy is `disableXiaomiForceDarkMode`.

The new test sets a light day theme with the default blue palette and no dynamic color, which is exactly what `Theme_Light` already resolves to, so its primary-color and window-background assertions hold whether or not `Themes.setTheme` runs. It pins the manifest removal, which the unchanged ManifestThemeTest already enforces, but not the call.

In the plan doc, only the Worktree line is still ahead of the tree.

Outside the delta, `Themes.setTheme` calls `setTheme(Context)` a second time after `applyDynamicColor`. That second call re-applies the palette overlay over the wallpaper colors whenever a non-blue palette and dynamic color are both on, a state users can reach. Classic screens, and now the import page, then show the palette's primaries while the Compose UI follows the wallpaper.

### What the host skips from AnkiActivity, and the palette ordering

AnkiActivity and `AbstractIntentHandler` follow `Themes.setTheme` with `disableXiaomiForceDarkMode(this)`, which adds `ThemeOverlay.Xiaomi` (`android:forceDarkAllowed=false` on API 29+). The import host didn't need it while it was pinned to a dark theme, since force dark only acts on light themes. With an explicit light Expressive theme on a device in dark mode, MIUI's per-app force dark can now darken it; that's the case the upstream opt-out exists for. `ExpressiveHomeActivity` doesn't apply the opt-out either, so the gap is app-wide. The import page stands out because it's View-based and its comment claims parity with AnkiActivity.

The ordering bug:

```kotlin
setTheme(activity)            // base theme + palette overlay
applyDynamicColor(activity)   // wallpaper overlay; KDoc: "Runs LAST so wallpaper colors win"
// ...
setTheme(activity as Context) // same style id is a no-op, but applyColorPalette() runs again
```

The palette overlays set `colorPrimary`, `colorOnPrimary`, and the primary, secondary, and tertiary container pairs, so those roles end up static while the surfaces stay dynamic. `SettingsScreen` turns dynamic color off when a palette is picked, but turning dynamic color back on keeps the chosen `paletteKey`. `ExpressiveImportPageActivityTest` runs with dynamic color off and the blue palette, so it can't catch this.

### Pinning the call in ExpressiveImportPageActivityTest

Without the call the activity keeps `Theme_Light` from `<application>`, so a night-theme case fails where the light one passes:

```kotlin
PrefsRepository(targetContext).apply {
    appTheme = AppTheme.NIGHT
    nightTheme = NightTheme.DARK
}
// ...
assertEquals(ContextCompat.getColor(targetContext, R.color.m3_primary_dark), activity.toMaterial3ColorScheme().primary.toArgb())
```
