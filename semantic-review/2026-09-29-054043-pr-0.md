# Native Expressive backup, restore, and collection maintenance

This third pass re-reviews Task 13 after round two's six fixes, and all six hold on the paths I traced: a manual backup of an unchanged collection writes nothing while a current backup exists and refuses to close the collection under a running media sync, restore always writes its own safety file, a finished media sync's stored error no longer fails anything, the restore outcome separates quarantined from pending media, `importColpkg` settles a retained journal before replacing, and the new tests run the real backend. The `newestBackupCoversCollection` heuristic is used only by manual Create backup, never by restore, and is sound enough for that non-destructive action. The quarantine merge and delete operations (their admission, queue placement, and journal interplay), the saved-state codec (no version bump needed), and the new notice and dialog raise nothing new. What remains sits mostly in the rare state where a committed restore could not finish. **Watch for:** **confirmed P3** the new `importColpkg` refusal reaches Transfer as a generic "Import did not complete" (and deletes the staged package) and Classic as a raw exception with a crash report; **confirmed P3** the deferred finish run by the startup sweep, `prepare`, and `discard` merges media into the live folder with the collection open and no media-sync check, which the Sync exclusion row says cannot happen; **confirmed P3, non-blocking** the heuristic compares write times, so after a failed or deleted newest backup an older file whose write overlapped the last change can produce "No changes since the latest backup."

**Verdict**: NEEDS_CHANGES

## High-level view

Manual Create backup consults `newestBackupCoversCollection()` only after the backend has skipped a forced backup as unchanged, so the heuristic only decides whether the last attempt's file still stands. Restore never consults it: `createSafetyBackup()` writes an explicit copy whenever the backend does not start a backup. The proxy, any listed backup with an mtime at least `col.mod`, errs toward an unneeded copy, except when the newest attempt failed or was deleted and an older file's write overlapped the last change, or a file was copied into the folder. A retry then reports "No changes since the latest backup." (**confirmed P3, non-blocking**).

The deferred finish is the one writer of the live media folder still without the round-two media-sync guard. `settleExpressiveRestore()` finishes a retained COMPLETE journal from the startup sweep, from `prepare`, and from `discard`, all with the collection open, so it can merge into a folder that a running media sync is using (**confirmed P3**).

`importColpkg`'s close step finishes or rolls back a retained journal after the strict close, and refuses with `ExpressiveRestorePendingException` if the journal survives. The replacement protocol holds, but the refusal is reported badly: Transfer's catch-all turns it into IMPORT_FAILED and deletes the staged package, and Classic's `launchCatchingTask` shows the exception's class name and sends a crash report on dismiss (**confirmed P3**).

Not tested: the deferred finish under a running media sync, and Transfer's and Classic's handling of the refusal. One new gateway test depends on file-system and backend clocks, as described with the heuristic below.

## `newestBackupCoversCollection` on the manual path

```
Manual Create backup (CREATE_BACKUP; not media-exclusive at admission)
  backupMutex
    backend create_backup(force = true)            queue; skipped when col.mod equals the last attempt's stamp
    ├─ started → await → true                      "Backup created."
    └─ skipped
        ├─ any listed backup mtime ≥ col.mod → false         "No changes since the latest backup."
        ├─ isMediaSyncRunning → MediaSyncActiveException     off queue
        └─ explicit COLPKG export → true                     queue: close, export, reopen; clears undo

Restore (commitRestore)
  isMediaSyncRunning → refuse                      off queue
  createSafetyBackup: backend backup, or explicit copy when skipped      no heuristic
  ExpressiveRestoreStaging.commit → activation     in-queue media-sync recheck
```

The backend skips a forced backup only while `col.mod` still equals the stamp it recorded when its last attempt in the same open collection started. Any close and reopen (an explicit copy, a restore, a COLPKG import, a full sync) resets that stamp, and the next backup is written. The heuristic is therefore reached only when the last attempt's snapshot already holds the current collection, and it has to decide whether that attempt's file still exists. It checks whether any listed backup was last written at or after `col.mod` (`ExpressiveMaintenanceCoordinator.kt:476-480`).

The proxy is wrong in the unsafe direction when an older file satisfies it without holding the last change. A backend backup snapshots the database inside the queue and writes the file afterwards on its own thread, with the queue free; on a large collection that write takes seconds, and the automatic backup starts one second after Home resumes. If the user's last change lands during that write, the older file's mtime is later than `col.mod`, yet its snapshot lacks the change. The backend still writes the next forced attempt, because the stamp changed. Only when that attempt fails (a full disk is the likely cause, and the user has just seen BACKUP_FAILED) or its file is deleted does a retry reach the heuristic, which then answers "No changes since the latest backup." Under the same precondition, a backup copied into the folder by a file manager, which gets a fresh mtime, satisfies the proxy too. The other direction is safe: a covering file stamped slightly before `col.mod`, for example because the kernel stamps mtime from its coarse clock, only costs an unneeded explicit copy.

**Confirmed P3, non-blocking.** The outcome is a misleading message on a non-destructive action, reached only after a failed or deleted latest backup. Comparing the snapshot instead of the write time closes it: for example, remember the `col.mod` and the file of this gateway's last successful backup, and require that file to still exist, falling back to the explicit copy otherwise. The positive-branch test, `a manual backup of an unchanged collection writes nothing when the newest backup is current`, relies on the same clocks: it passes because the backend finishes writing a few milliseconds after the note it covers.

The explicit copy's media-sync check runs before, not inside, the export's queue block, so the Sync exclusion row's "rechecked inside the collection queue" does not describe it.

## The deferred finish merges without the media-sync guard

**Confirmed P3.** `settleExpressiveRestore()` (`CollectionManager.kt:501-515`) calls `finishCompletedExpressiveRestore()` for a retained COMPLETE journal, which renames staged media into `collection.media` and quarantines the rest. Three callers reach it with the collection open: the startup sweep (`cleanupInterruptedArtifacts()` → `discard(null)`, `ExpressiveMaintenanceCoordinator.kt:1221`, `:736`), `ExpressiveRestoreStaging.prepare()` (`:698`), and every `discard(generation)`. None checks `isMediaSyncRunning()`, and PREPARE_RESTORE is not media-exclusive at admission. `SyncMediaWorker` starts the sync outside the queue and the backend runs it independently, so an Activity instance created while one is running, or a restore preparation during one, merges into the folder the sync is scanning and writing. The finish inside activation is covered by its in-queue check, and the finishes in `ensureOpenInner()` and `importColpkg()` run only after the collection is closed, which ends any media sync.

The state is rare: the journal survives only when the quarantine itself failed, most likely on a full disk. It is, however, the state round two made durable, and the Sync exclusion row (`PARITY_CONTRACT.md:169`) lists restore among the operations that never overlap a running media sync. In the COMPLETE branch, when the collection is open, leave the journal for the next settle while a media sync runs, and have `prepare` report that as MEDIA_SYNC_ACTIVE rather than PREVIOUS_RESTORE_UNFINISHED. A gateway test with `mediaSyncStatusForTesting = { true }` over the retained journal from the existing `broken` obstacle test would pin it.

## `importColpkg` refusal reaches Transfer and Classic untyped

`importColpkg`'s close step (`CollectionManager.kt:1093-1119`) throws the refusal before `replace` runs in `runStrictCollectionReplacementProtocol()`, so nothing is imported, the reopen opens the restored database again, and `runCommittedCollectionReplacement()` (`ExpressiveTransferCoordinator.kt:701-714`) rethrows it without invalidating. The test `a collection package import settles a retained restore journal before replacing` pins both the refusal and the settle-then-replace.

**Confirmed P3.** `confirmImport()`'s catch-all (`ExpressiveTransferCoordinator.kt:971-985`) maps the refusal to IMPORT_FAILED, "Import did not complete. No private provider details are shown or retained.", and deletes the staged package. Nothing tells the user that an earlier restore is blocking the import, that the collection is unchanged, or what would clear it, and every retry needs the file picked again. Classic's COLPKG import and restore share this function (`BackendBackups.kt:31-44`). There the exception falls to `launchCatchingTask`'s generic branch (`CoroutineHelpers.kt:224`), which shows `com.ichi2.anki.ExpressiveRestorePendingException: An earlier Expressive restore has not finished` and sends a crash report when the dialog is dismissed; Classic stays reachable through the UI preference. Give Transfer a typed error with Maintenance's PREVIOUS_RESTORE_UNFINISHED wording, handle the exception in Classic before the generic branch (localized, no report), and note the reporting in the "COLPKG import after a restore" row (`PARITY_CONTRACT.md:163`).
