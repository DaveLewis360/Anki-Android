## Media-sync checks see a running sync, not one about to start

```
SyncMediaWorker thread                          collection queue
  getColUnsafe()  ── blockForQueue ──────────►  open, return the collection
                                                next task: settle, COMPLETE journal
                                                  read journal
                                                  isMediaSyncRunning() → false
  backend.syncMedia(auth)   (queue released)      finishCompletedExpressiveRestore()
    backend thread scans and changes                rename staged media into collection.media
    collection.media
```

**Likely P3, non-blocking.** `activatePreparedExpressiveRestore()` justifies its check with "a media sync cannot start while the database is swapped and media is merged, because the media worker obtains the collection through this queue" (`CollectionManager.kt:538-539`). This round's deferred-finish check in `settleExpressiveRestore()` (`:511-514`) relies on the same premise. The worker does obtain the collection through the queue, but it starts the sync only after the queue has let go: `SyncMediaWorker.syncMedia()` reads `CollectionManager.getColUnsafe().backend` and then calls `backend.syncMedia(input = auth)` (`SyncMediaWorker.kt:84-85`). If the next queued task is a deferred finish, an activation, or a media operation, it can reach its check before the worker thread makes that call. The backend runs the sync on its own thread and takes the collection only between the task's backend calls, so the sync then runs while the task works on the media folder.

The window is the time between `blockForQueue` returning on the worker thread and the `syncMedia` call. It matters most for the deferred finish: the check follows a few milliseconds of journal I/O and the merge starts right after it, so a worker thread scheduled late, for example at app start when the sweep runs, overlaps the merge. That is the overlap round three set out to exclude, reached only with a retained COMPLETE journal. In activation, the close right after the check aborts a sync that starts in between, so overlapping its merge needs a worker delayed past the whole swap.

Calling `syncMedia` inside the queue closes the window: `withCol { backend.syncMedia(input = auth) }`. The worker polls the status a second after the call, so the call only starts the backend's sync and would not hold the queue while it runs. Every in-queue check then either sees the sync or runs before it can start. `SyncMediaWorker` belongs to the sync work, not Task 13. If it stays as it is, reword the activation comment so it promises only that a media sync already running is refused, which is what the Sync exclusion row (`PARITY_CONTRACT.md:169`) states.

## The snapshot record behind "No changes since the latest backup."

```
Manual Create backup (backupMutex)
  list backups ─► queue: read col.mod, backend create_backup(force) ─► await ─► list again
  ├─ started: record (file found by the listing diff, stamp)            "Backup created."
  └─ skipped: record stamp == col.mod, file exists, current folder      "No changes since the latest backup."
              otherwise: media-sync check ─► explicit copy ─► record (copy, stamp read before the export)
```

The backend skips a forced backup only when its last attempt in the open collection already saw the current collection, so the record only has to say whether that attempt's file, or a later explicit copy, still holds it. A backend backup's stamp is read in the same queue task as its snapshot. An explicit copy's stamp is read before the export, so a change that lands in between leaves a record older than its file. A failed attempt, a cancelled await, or a same-named rewrite within one mtime tick leaves the previous record, whose stamp stops matching once anything has changed. The one backup in the Expressive app that bypasses this gateway, `SyncWorker`'s full-download backup, is followed by a close, after which the backend always starts the next attempt. Each case therefore ends in an explicit copy, never in a wrong "No changes". Round three's two cases, a change during a slow write and a copied-in file, change `col.mod` or are never recorded.

**Confirmed nit.** The gateway interface KDoc (`ExpressiveMaintenanceCoordinator.kt:322-325`) still says the copy is skipped when "the newest backup is at least as new as the collection's last change", the rule this round removed. The `Terminal` KDoc (`:291`) and the test name `a manual backup of an unchanged collection writes nothing when the newest backup is current` still speak of the newest backup.

**Confirmed nit.** No test reaches the mismatch side of the stamp comparison (`:505`). The unchanged-collection test takes the match, and the two manual-backup tests that delete every backup stop at the missing file. A test that backs up, adds a note, fails the next backup with the regular-file backup folder that the safety-backup tests use, restores the folder, and expects `true` with an app-clock name would pin round three's scenario.

I did not run Gradle, lint, or tests. `rslib` is not available locally, so the backend behaviour behind the first section (a media sync started by `syncMedia` runs on its own thread and takes the collection only between calls, and closing the collection aborts it) comes from Anki's source as I know it, not from a local read.
