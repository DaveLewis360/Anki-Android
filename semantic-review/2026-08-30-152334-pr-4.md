# Classic migration completion recovery hardening

Task 4 now restores the completion preference from a durable `COMPLETE` journal before removing recovery artifacts, and public recovery maps operational failures into its `Blocked` result. The first prior P2 is closed. The second is partially open: exception mapping is fixed, but finalization cleanup can still lose or bypass the collection-closed invariant. Watch for: **P2, confirmed** a failed collection close is swallowed and recovery’s guard then sees `null`; **P2, likely** cancellation while returning from activation can leave an open migrated collection with an `ACTIVATED` journal.

**Verdict**: NEEDS_CHANGES

## High-level view

A valid `COMPLETE` journal is now authoritative. Normal completion and recovery synchronously commit `expressive.classic_migration.completed` before deleting rollback, stage, journal, or temporary-journal artifacts, so a failed preference commit preserves the journal for retry.

Public recovery rethrows `CancellationException` and converts other queue, guard, and filesystem-entry exceptions to `ExistingProfileRecoveryResult.Blocked`. The Activity renders that result as a recoverable failure.

The post-activation catch requests collection closure before rethrowing ordinary finalization failures, but `ensureClosed()` swallows `Collection.close()` exceptions and clears the manager’s reference. The queue-held activation call also sits outside that catch, leaving a cancellation window after activation opens the collection but before finalization begins.

<details><summary>Details</summary>

## `COMPLETE` journal reconciliation — prior finding 1 CLOSED

**CLOSED, confirmed:** `activate()` executes `writeJournal(... COMPLETE)`, then `markMigrationCompleted(preferences)`, and only afterward deletes rollback and journal artifacts. `markMigrationCompleted()` uses `SharedPreferences.Editor.commit()` and throws when it returns false, so commit failure leaves the valid `COMPLETE` journal intact.

Recovery has the same ordering: the `MigrationPhase.COMPLETE` branch calls `markMigrationCompleted(preferences)` before deleting rollback and stage, and the common journal deletions occur after the branch. Its enclosing catch maps commit failure to `Blocked` without removing the journal.

## Guard and queue exception mapping — prior finding 2 mapping CLOSED

**CLOSED, confirmed:** `recoverInterruptedMigration()` wraps mutex acquisition, `Dispatchers.IO`, and `CollectionManager.withCollectionClosedForRecovery()` in one public `try`. It rethrows `CancellationException`; the following `Exception` catch returns `ExistingProfileRecoveryResult.Blocked`. This covers the guard’s `IllegalStateException` and non-cancellation queue-dispatch failures, and `ExistingProfileMigrationActivity.recoverAndContinue()` handles `Blocked` as a failed recovery state.

## Failed close is hidden from the recovery guard — prior finding 2 remains OPEN

**P2, confirmed:** ordinary finalization failure now calls `CollectionManager.ensureClosed()`, which delegates to `ensureClosedInner()`. If `current.close()` throws, `ensureClosedInner()` catches and logs the exception, then unconditionally sets `collection = null`. `withCollectionClosedForRecovery()` checks only `collection?.dbClosed != false`, so recovery is admitted even though closure failed and the old native collection handle may still own the activated files.

Use a strict queue-held close for this transition, equivalent to the strict close used before activation. A failed close must preserve the manager reference and make public recovery return `Blocked` without renaming or deleting migration paths.

## Activation-return cancellation bypasses finalization cleanup

**P2, likely:** `CollectionManager.activateCollectionDirectory(...)` is called before the `try` that writes `COMPLETE` and closes on failure. Its non-suspending queue block can rename stage to target and open the migrated collection while the caller is canceled; dispatch back to the canceled caller can then throw `CancellationException` instead of returning, outside the finalization catch.

The outer cancellation handler only cleans `COPYING` or `READY`, leaving an `ACTIVATED` journal and open collection. Recovery then maps the open-collection guard to `Blocked` but cannot progress until process teardown. Enclose activation and finalization in a cleanup boundary that closes in `NonCancellable` context whenever activation may have committed.
