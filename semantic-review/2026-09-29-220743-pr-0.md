## High-level view

With dynamic color at the end of `setTheme(Context)`, that method is the one place that sets the overlay order. The Activity overload keeps its sequence: manifest background read, fail-fast check, theme, palette, dynamic color, splash replacement. The TTS dialog's `Themes.setTheme(requireContext())` runs on the host activity, so it now ends with the wallpaper overlay too. Non-Activity contexts are unchanged, because `applyDynamicColor` still skips them.

In production, `PrefsRepository(context)` and `Prefs` wrap the same default SharedPreferences instance, so the palette read doesn't change. Theme and palette now both come from `PrefsRepository(context)`, and dynamic color comes from `ExpressiveSettings`' own prefs file. The restore path therefore never reaches `AnkiDroidApp.instance` through `Themes`. In Robolectric the palette's writer and reader now go through different objects, and no current test depends on that.

The palette leak is gone. ThemesTest no longer writes through `Prefs`, and `ExpressiveSettings.save` doesn't call `syncToClassicThemePrefs`. By reading (not run red), the palette test's second `Themes.setTheme(activity)` fails if dynamic color leaves the Context overload. The splash test's new assertion shows that the wallpaper overlay reaches `windowBackground`. A replacement resolved before the overlay now fails the test, but only while the two backgrounds differ.

### What the splash test does and doesn't guard

Theme_Light sets `android:windowBackground` to `?android:attr/colorBackground`, and Material 1.14.0's `ThemeOverlay.Material3.DynamicColors.Light` overrides `android:colorBackground`. On the Robolectric SDK 35 jar, `m3_sys_color_dynamic_light_background` (v34: `@android:color/system_background_light`) resolves to `#FAF8FF`, and the static `m3_background_light` is `#F8F9FF`. If the replacement ran before `applyDynamicColor`, the decor would hold `#F8F9FF` while `tv.data` is `#FAF8FF`, and the last assertion would fail. **Confirmed:** nothing keeps those two values apart. If either one moves, the test passes on both orders without any warning. The palette test already has this kind of guard for primaries:

```kotlin
val static = ContextCompat.getColor(activity, R.color.m3_background_light)
assumeTrue("the wallpaper background differs from the static one", wallpaper != static)
```

### TTS re-application on the Reviewer

The test's `ThemedActivity` still has the user's style as its theme resource. The second `setTheme` therefore does nothing, and only the palette and dynamic color are re-applied. The Reviewer, one of the dialog's hosts, keeps `ThemeOverlay_DisableKeyboardHighlight` as its theme resource after `onCreate`. In the Reviewer, the call therefore re-applies the whole base style first. Dynamic color still ends up last, so the fix holds by reading. **Confirmed**, though: that variant isn't tested, and neither is the dialog itself. The run's `--tests com.ichi2.anki.dialogs.TtsVoicesDialogFragmentTest` filter matches no class.

### `Prefs` and per-context reads in tests

In Robolectric, `Prefs` keeps the SharedPreferences instance of the first test that touched it, and `PrefsRepository(context)` gets a fresh one per test. `ExpressiveSettings.syncToClassicThemePrefs()` still writes the palette through `Prefs`. **Confirmed mechanism, no current test affected:** a future test that picks a palette in the expressive UI and then checks a classic screen would read the default palette. Not tested: nothing fails without the restore-path fix. ActivityStartupUnderBackupTest wasn't in the run, and it can't reliably start with an uninitialized `Prefs` anyway.
