# Native Expressive backup, restore, and collection maintenance

This pass re-reviews Task 13 after the fixes for round one's eight issues. All eight fixes are in the code and hold on the paths I traced: a forced backup always leaves a restorable file, unowned staging is swept at every coordinator start and released on clear, unmerged media is quarantined instead of deleted, a queued media sync no longer blocks backups, the coordinator keeps only the application context and does its file and HTML work off Main, live regions are limited to stages, refusals, and summaries, the unused strings are gone, and most failure boundaries have real-backend tests. Two of the fixes changed how maintenance meets media sync, and both introduce new failure modes. **Watch for:** **likely P2** the explicit copy behind a manual "Create backup" closes the collection, which aborts a running media sync; **likely P3** the new `mediaSyncStatus()` rechecks rethrow a finished media sync's stored error, failing a restore and discarding its validated staging; **confirmed P3** `finishPending` shows the media warning for cleanup-only failures and drops the quarantine count; **confirmed P3** Transfer's `importColpkg` finishes or rolls back a retained restore journal after its own replacement; **confirmed P3** the new failure branches are partly untested and four contract rows overstate.

**Verdict**: NEEDS_CHANGES

## High-level view

When the backend reports an unchanged collection, the gateway now writes a COLPKG into the backup folder under `backupMutex`, names it like a backend backup from `TimeManager`, and checks that it is non-empty; restore turns any backup failure into `SafetyBackupException` before anything changes. The copy is a full export, which closes and reopens the collection inside the queue. Restore refuses a running media sync before it gets there. Manual Create backup does not, so the close aborts the sync and clears undo history (**likely P2**).

The three new `mediaSyncStatus()` rechecks (before the safety backup, inside activation, and inside the media operations) close the gap round one left for Classic `SYNC_MEDIA` work. That call also rethrows, once, the error of a media sync that has already ended. `SyncMediaWorker` never polls again after cancelling, so a media sync stopped by WorkManager leaves an `Interrupted` error behind. The next restore confirmation then fails as RESTORE_FAILED and discards its validated staging, and the next media action fails generically (**likely P3**).

Apart from that throw, the new exception paths keep staging ownership consistent. The one non-obvious case is a preparation cancelled mid-import: it keeps the staging mutex until the blocking import returns and then sweeps its own result, so neither the startup sweep nor a new preparation can race it.

Restored media is no longer dropped: files that cannot be merged move to `broken/expressive-restore-media-N`, and any failure in finish keeps the COMPLETE journal and staging for the next settle or open. `finishPending` is coarse, though. It is set for any failure in finish, so a cleanup-only failure reports media that "could not be added" after every file was merged, and a quarantine that already happened is never reported (**confirmed P3**). A retained journal is also finished, or rolled back, by whatever opens the collection next, and Transfer's `importColpkg` reopens right after writing its own package (**confirmed P3**).

The saved-state codec needs no version bump for the two new error values: unknown names decode to `null` and render the generic failure, and a ConfirmRestore, including its `blockedBy`, is persisted as an interrupted preparation, matching the sweep that deletes its staging after process death. Several new failure branches and three Activity wirings are still untested, and four PARITY rows overstate what is covered (**confirmed P3**).

## The explicit safety copy closes the collection

```
confirmRestore ─► commitRestore
                   ├─ mediaSyncStatus()                     off queue; refuse if active
                   ├─ createBackup(force = true)            backupMutex
                   │    ├─ backend create_backup            queue; false if unchanged
                   │    └─ false → exportCollectionPackageGuaranteed
                   │               queue: close(forFullSync) → export → reopen
                   └─ ExpressiveRestoreStaging.commit       staging mutex
                        └─ activatePreparedExpressiveRestore   queue
                             ├─ mediaSyncStatus()            in-queue recheck
                             └─ PARKING → PARKED → ACTIVATED → open → COMPLETE → finish

Manual "Create backup" ─► createBackup(force = true)        no media-sync check
```

**Likely P2.** The explicit copy in `createBackup()` (`ExpressiveMaintenanceCoordinator.kt:396-438`) runs whenever the backend returns `false`, which it does whenever the collection is unchanged since its last backup attempt, whether or not that attempt left a file. The copy is written by `exportCollectionPackageGuaranteed()` (`CollectionManager.kt:1050-1075`), which takes the open collection away from the backend. The wrapper closes with `forFullSync = true`, the backend's export consumes and closes the collection, and `reopen()` opens it again. In Anki's backend, closing the collection or exporting a package first aborts a running media sync and waits for it to stop.

Restore is not affected: `commitRestore()` refuses a running media sync before the backup (`:476`), and the collection is about to be replaced anyway. Manual CREATE_BACKUP takes the same branch without that check. It is neither sync- nor media-exclusive, so admission lets it start during a media sync. The branch runs whenever the user creates a backup and nothing has changed since the last attempt, for example by tapping Create backup twice, or once after the automatic backup that runs on resume. The media sync then ends early. `SyncMediaWorker.monitorProgress()` (`SyncMediaWorker.kt:94-107`) either sees an inactive sync and reports success, or its next status call gets the backend's `Interrupted` error and it reports a failed media sync with a connection-error notification. Closing the collection also clears the backend's undo history.

For CREATE_BACKUP, check `mediaSyncStatus()` before taking the export branch and refuse with `MediaSyncActiveException`, which already maps to MEDIA_SYNC_ACTIVE, or report that nothing has changed since the last backup. Either way, document the close in the Manual backup row. I could not read `rslib` locally. The abort on close and export is Anki's backend behaviour; the Kotlin side (close, export, reopen, no admission check) is confirmed.

## `mediaSyncStatus()` rethrows a finished sync's error

**Likely P3.** The backend reports a background media sync's outcome through the next `mediaSyncStatus()` call. AnkiDroid's Classic monitor documents this ("this will throw if the sync exited with an error", `Sync.kt:412`) and catches `BackendInterruptedException` after an abort (`:422`). `SyncMediaWorker` consumes that result only while it is still polling. On cancellation, it calls `cancelMediaSync()` and rethrows without polling again (`SyncMediaWorker.kt:67-71`). Cancellation comes from the notification's Cancel action, from the Expressive cancel, or from WorkManager stopping an unmetered-only job when Wi-Fi drops. The interruption then stays stored until the next media sync starts.

None of the three new rechecks handles a throwing status. In `commitRestore()`, `mediaSyncActive()` (`:494`) throws before the safety backup. The exception is not `ExpressiveRestoreBlockedByMediaSyncException` and is not wrapped, so `confirmRestore()`'s generic catch (`:990-996`) discards the validated staging and the external COLPKG copy, and shows "The backup could not be restored". The in-queue check in `activatePreparedExpressiveRestore()` (`CollectionManager.kt:468`) would do the same through `ExpressiveRestoreStaging.commit()`'s generic catch. `requireNoMediaSync()` (`:560-562`) turns the next media check, trash, or rebuild action into MAINTENANCE_FAILED. Each happens once, because the call consumes the stored error, and a retry works. For a restore, though, retrying means picking and validating the package again, after a message that blames the backup.

Wrap the three checks in one helper that treats a thrown status as "not running" and logs it. At minimum, keep the staging when the pre-check throws.

## `finishPending` covers more than media

**Confirmed P3.** `finishCompletedExpressiveRestore()` (`CollectionManager.kt:652-664`) merges media, quarantines what is left, then deletes the parked database, the staging directory, and the journal. On any exception it returns `ExpressiveRestoreOutcome(finishPending = true)` with a zero quarantine count. The coordinator maps that to RESTORED_MEDIA_PENDING, whose text says some restored media "could not be added to your media folder yet… adding them is retried the next time the app starts". Two cases contradict that text. If every file merged and only a deletion failed, no media is pending. If the quarantine succeeded and a later deletion failed, the files are already in `broken/`; the retry finds no staged media folder, and the user is never told where the files went. A quarantine performed by a deferred finish at the next settle or open is only logged.

Return the quarantine count alongside `finishPending`, show the media warning only while staged media remains, and record a deferred quarantine so the next Maintenance visit can show it. The unbounded retry that round one asked to bound is now reached only if the quarantine or cleanup keeps failing. While it does, every preparation fails with the generic "The operation could not be completed."

## A retained journal is settled by whoever opens next

**Confirmed P3, narrow.** Recovery runs in `ensureOpenInner()` whenever a closed collection opens (`CollectionManager.kt:810-816`). Transfer's COLPKG replacement uses `importColpkg()` (`:1022-1042`, called from `ExpressiveTransferCoordinator.kt:729`). It closes the collection, lets the backend write the new database and extract its media into `collection.media`, and then reopens through `ensureOpenInner()`. If a COMPLETE journal is still retained, that reopen merges the earlier restore's leftover staged media over same-named files that the new package just wrote. If an uncommitted journal is retained (a failed rollback whose immediate retry also failed), and the rollback now succeeds, it replaces the imported database with the pre-restore one while Transfer reports success. Both cases need a retained journal in the same session, which `finishPending` now makes more likely. Settle the restore journal inside `importColpkg`'s queue block before replacing, or refuse the replacement while `hasExpressiveRestoreArtifacts()` is true.

## Tests and contract after this round

The gateway tests run the real backend and have no timing dependence I could find. The backend's unchanged check compares the modification stamp it recorded at the last attempt, the explicit-copy tests assert the `MockTime` name so they prove that branch ran, and the quarantine test forces its rename failure with a same-named non-empty directory. The coordinator's new media-sync, safety-backup, outcome, `onCleared`, and sweep tests all go through a fake gateway.

**Confirmed P3.** Not tested: `finishCompletedExpressiveRestore()`'s failure branch with real files (for example, a regular file named `broken` plus an unmergeable file), which would pin the retained journal, the refused preparation, and completion by the sweep; the ownership hand-back in `ExpressiveRestoreStaging.commit()` after an in-queue media-sync refusal, where only a fake throws; a `mediaSyncStatus()` that throws; a failing explicit export; and, at Activity level, picker routing, the resume-driven automatic backup, and `requestSync()` refusal while maintenance blocks sync.

**Confirmed P3.** Four PARITY rows overstate. "Manual backup" (`:158`) omits the close and reopen. "Restored media" (`:162`) says quarantined files are reported, which is not true for a deferred finish. "Sync exclusion" (`:168`) marks "a refused restore keeps its staging" as covered by a fake-gateway test, and says only restore and media work exclude a running media sync. "Automatic backup" (`:159`) omits the Transfer collection-blocking gate that the Activity effect also applies.

I did not run Gradle, lint, or tests. `rslib` is not available locally, so two backend behaviours are inferred from Anki's backend and from AnkiDroid's own Classic monitor: the media-sync abort on close and export, and the once-only error reporting.
