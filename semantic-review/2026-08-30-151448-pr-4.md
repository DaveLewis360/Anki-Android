Task 4 now falls back from a malformed temporary journal to a valid stable journal, serializes migration and recovery through one process mutex, and places recovery under the collection queue. Cancellation propagation, working-state back blocking, and orientation/screen-size handling close the prior lifecycle finding. Two completion windows remain: a `COMPLETE` journal does not restore a missing completion preference, and post-activation persistence or cleanup failures leave an open collection that recovery refuses. ## High-level view

The malformed-temporary-journal finding is closed because temporary and stable candidates are parsed independently. The destructive concurrent-recovery finding is closed because migration and recovery share `migrationMutex`, while activation and recovery both participate in the collection queue.

Cancellation swallowing and back-abandonment are closed, but result-loss protection remains incomplete: the journal reaches `COMPLETE` before the durable preference exists, while recovery treats `COMPLETE` as cleanup-only. Failures after activation also leave the migrated collection open, so the new guard prevents the recovery path from reconciling that state.

## `COMPLETE` recovery preserves the target but loses the durable result

**P2, confirmed:** `activate()` writes `MigrationPhase.COMPLETE` before calling `preferences.edit().putBoolean(PREF_MIGRATION_COMPLETED, true).commit()`. Process death between those durable writes leaves the activated target and a valid `COMPLETE` journal, but no completion preference.

`recoverInterruptedMigrationUnlocked()` handles `COMPLETE` by deleting rollback and staging artifacts, then both journal files, without committing `PREF_MIGRATION_COMPLETED`. DeckPicker consequently launches Introduction again; Copy Classic then fails because the migrated target is no longer pristine. Recovery should treat a matching `COMPLETE` journal as authoritative and durably commit the preference before deleting it.

## Post-activation failures cannot pass the recovery guard

**P2, confirmed:** `CollectionManager.activateCollectionDirectory()` opens the migrated collection before returning. If the subsequent `COMPLETE` write, preference commit, or rollback cleanup fails, `migrate()` reports failure while the activated collection remains open and a journal remains present.

A retry enters `withCollectionClosedForRecovery`, which rejects the open collection before inspecting the journal. The migration Activity maps this to a normal retry failure, but recovery-only `recoverAndContinue()` has no exception mapping around `recoverInterruptedMigration()`, so the guard failure escapes its lifecycle coroutine instead of becoming `ExistingProfileRecoveryResult.Blocked`. Close the collection before exposing retry, or provide a queue-held completion reconciliation that is safe for an already activated collection.
