# Native expressive deck management and Custom Study parity

Task 5 turns Expressive Home into a hierarchy-aware deck manager: parent rows remain directly studyable while their chevrons independently control expansion, deck operations run through the serialized collection repository, and regular versus filtered decks receive distinct menus and option routes. Custom Study exposes all six backend actions and hands a created session directly to Study by the backend-selected deck ID. Collection invalidations, Activity resume, and sync completion refresh Home, while deletion uses a child-inclusive preview and exact-top undo token. Watch for: **confirmed P2** — “Create subdeck” does not bind creation to the selected parent, so editing the prefilled qualified name can create a deck elsewhere in the hierarchy.

**Verdict**: NEEDS_CHANGES

## High-level view

The Home tree separates row activation from expansion, reads the persisted selected deck, and recursively counts the complete hierarchy even when descendants are collapsed. Mutations publish normalized `OpChanges`, and Home combines the active change stream with resume and sync refresh keys.

Deletion previews include descendants, reports the backend removal count, and permits undo only while the captured backend step remains exactly on top. Regular decks expose Custom Study and subdeck creation; filtered decks replace those actions with Rebuild and Empty.

Custom Study maps all six modes to backend request fields, preserves signed limit deltas, carries cram card-state and include/exclude tags, and blocks duplicate submission. Session calls capture `decks.selected()` inside the serialized write after `sched.customStudy()`, matching the backend’s generated-deck selection behavior without an English-name lookup.

Normal options open the backend-owned `deck-options/{deckId}` feature in `SingleFragmentActivity`; filtered options open `FilteredDeckOptionsFragment` in `ConfigAwareSingleFragmentActivity`. Neither enters `DeckPicker`, and `ExpressiveHomeActivity.onResume()` refreshes Home when either returns.

## “Create subdeck” can create outside the selected parent

**Confirmed P2:** choosing “Create subdeck” stores the selected `UiDeck`, but the dialog receives `${parent.fullDeckName}::` only as editable initial text (`HomeScreen.kt:194-198`, `HomeScreen.kt:349-354`). Submission passes the edited string to the same `createDeck(name)` method used for top-level creation (`HomeScreen.kt:361-369`), and the gateway has no parent argument or ancestry check (`ExpressiveDeckGateway.kt:34`, `ExpressiveCollection.kt:202-213`). Erasing or replacing the prefix successfully creates `Other`, `Sibling::Child`, or a child beneath another parent while the action remains labeled “New subdeck”.

Classic accepts leaf text and derives the qualified name from the selected parent ID with `decks.getSubdeckName(parentId, text)` (`CreateDeckDialog.kt:121-126`, `CreateDeckDialog.kt:159-177`). A parent-aware gateway operation would preserve that invariant, apply duplicate validation to the actual fully qualified destination, and prevent editable or stale UI text from redirecting creation.
