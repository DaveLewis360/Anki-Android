# Splash-first theme order, with dynamic color applied after the palette

`Themes.setTheme(activity, savedInstanceState)` goes back to upstream's order. It reads the manifest theme's `windowBackground`, runs the fail-fast decor check, applies the user's theme and palette once, applies dynamic color, and then replaces the launcher splash background. This undoes both regressions from 29edb22b3a. `hadLauncherSplash` can be true again, so DeckPicker, CardBrowser, Reviewer and IntentHandler2 drop `launch_screen`, and the palette overlay no longer lands on top of the wallpaper colors. Two new ThemesTest cases fail on the old order and pass on the new one, and the green run started after the last source edit.

**Watch for:** **confirmed** the dynamic-color test sets `Prefs.colorPalette = "rose"` and never resets it. `Prefs` is a process-wide object, so every later test in the fork gets the rose overlay. **Likely, pre-existing:** TtsVoicesDialogFragment calls the Context overload, not the bundle one, and that overload still re-applies the palette over dynamic color on the host activity. **Likely, pre-existing:** on the restore-from-backup path, `applyColorPalette` reads `Prefs`, and initializing `Prefs` needs the `AnkiDroidApp.instance` that this path doesn't have. All non-blocking for this diff.

**Verdict**: APPROVED

## High-level view

The four `(Activity, Bundle)` callers now get the same sequence. IntentHandler2 enters through AbstractIntentHandler after the plain `Activity.onCreate`, which doesn't build the decor. Its `Theme_Dark.Launcher` makes it a splash case alongside DeckPicker, CardBrowser and Reviewer. TtsVoicesDialogFragment isn't one of these callers. It uses the Context overload, which this diff doesn't touch and which still ends with the palette on top. The AppLoadedFromBackupWorkaround path throws at the palette read before it reaches the reordered steps. That throw is pre-existing and happens for every theme except e-ink. E-ink and non-Activity contexts behave as before: both overlay helpers skip e-ink, and the Context overload never applied dynamic color.

Material 1.14.0's `ThemeUtils.applyThemeOverlay` (checked in the AAR bytecode) applies the overlay with `applyStyle(overlay, true)` to the activity theme. It touches the decor theme only through `peekDecorView()`. Called before `super.onCreate`, it lands on the theme that the window style and later inflation read. It also can't create the decor behind the fail-fast check, which again runs before any theme change. The v31 dynamic overlays set `android:colorBackground` but not `android:windowBackground`, so AnkiDroidApp's `onActivityPreCreated` overlay can't hide `launch_screen` from the `hadLauncherSplash` read. Because the replacement is resolved after dynamic color, splash activities get the wallpaper-derived background.

Both tests tell the two orders apart. The red run failed exactly these two: it got a `LayerDrawable`, and the rose primary `#984061` instead of the dynamic primary. The green run passed 286 tests in 21 classes, with no skips in ThemesTest. Neither test depends on timing or the device wallpaper, and in the fixed method order the palette test already runs after the night-mode test. The splash test turns dynamic color off, though it is on by default, so moving `applyDynamicColor` below the replacement would still pass both tests. Its early `window.windowStyle` read stands in for a platform trigger that upstream's 79b08adaec describes only by its symptom. The test therefore pins the ordering contract, not a known device path.

<summary>Details</summary>

### What each test pins

```
read windowBackground   <- splash test: the early windowStyle read makes the old order fail
fail-fast decor check   <- existing early-decor and recreation tests
setTheme(Context)          base style, then palette overlay
applyDynamicColor       <- palette test: rose saved, dynamic on, primary must be the dynamic one
splash replacement      <- nothing checks that this runs after applyDynamicColor
```

### Why the palette write outlives the test

`object Prefs : PrefsRepository(AnkiDroidApp.sharedPrefs(), …)` captures the SharedPreferences instance of the first test in the Robolectric sandbox. Robolectric's `ShadowContextImpl.reset()` nulls `ContextImpl.sSharedPrefsCache` between tests. Later tests therefore get fresh instances through `PrefsRepository(context)`, while `Prefs` keeps the old instance and its in-memory values. In the green run, ThemesTest ran first in a single fork, so the 20 classes after it already ran with the rose palette and passed. The full suite (`forkEvery = 40`) will put other classes after it. Upstream resets its `Prefs` writes in `finally` (CardBrowserFragmentTest, SortTypeTest).

### The Context overload and the restore path

The new KDoc says dynamic color must run after `applyColorPalette`, but the Context overload runs the palette with nothing after it. The `context !is Activity` guard in `applyDynamicColor` already allows it to live there:

```kotlin
fun setTheme(context: Context) {
    updateCurrentTheme(context)
    context.setTheme(currentTheme.styleResId)
    applyColorPalette(context)
    applyDynamicColor(context) // no-op for non-Activity contexts and e-ink
}
```

This keeps the Activity overload's order, with dynamic color before the splash replacement. It also gives M3ExpressiveDemoActivity, which calls the Context overload before `super.onCreate`, the same View colors. In the TTS case, the dialog's own views have already copied the activity theme by `onViewCreated`. The drift therefore shows up in what the Reviewer inflates afterwards.

Upstream's `Themes` read only `PrefsRepository(context)`, so the backup workaround could show its toast and exit. Since 29edb22b3a, every theme except e-ink reaches `Prefs.colorPalette`, and on that path the `Prefs` initializer throws. ActivityStartupUnderBackupTest is unlikely to catch this. It nulls `instance` after app startup, in a JVM that has already run other tests, so a `Prefs` object that was initialized earlier keeps working. Production has no such earlier initialization.
